## 2026-08-03 Phase 0: 分析パイプライン候補を実曲1曲で総当たり

- **対象曲**: RAU DEF - FREEZE!!! feat. Sugbabe（Prod. PUNPEE / 2017）。YouTube MV 音声 4:02.68
- **やったこと**: `tools/reference/` に Python 3.12 の venv を立て、demucs（4分割/6分割）・librosa・basic-pitch を
  通しで走らせた。レポートは `~/Music/daw/references/rau-def-freeze/report.md`

### 環境（動いた組み合わせ）

`torch 2.13.0 / torchaudio 2.11.0 / demucs 4.1.0 / librosa 0.11.0 / basic-pitch 0.3.0 / numpy 1.26.4`（Python 3.12・macOS arm64）

- **basic-pitch は 0.4.0 が入らない**: `tensorflow-macos<2.15.1` を要求するが py3.12 用 wheel が存在しない。0.3.0 で固定
- **basic-pitch 0.3.0 の依存が2つ壊れている**（どちらも実測で踏んだ）
  - `resampy<0.4.3` を指定するが 0.4.2 は setuptools 81+ で消えた `pkg_resources` に依存していて import 不能 → 0.4.3 で上書き
  - 既定の TF SavedModel が TF 2.16(Keras 3) で読めない → `build_icassp_2022_model_path(FilenameSuffix.onnx)` を明示
  - ピッチベンド推定で scipy 1.13 で移動した `scipy.signal.gaussian` を呼ぶ → `scipy.signal.windows.gaussian` を差す
- **demucs は MPS で動く**: 3:50 の曲が 4分割・6分割とも **15〜17秒**。想定より2桁速く、実験の回転が上がった
- yt-dlp は Brewfile に記載済みだが未インストールだった（＝LaLa のURL取り込みもこのマシンで動いていなかった）。導入して復活

### 精度の判定

| ツール/項目 | 判定 | 実測 |
|---|---|---|
| BPM（自作の剛体グリッド） | **使える** | 97.600 で鋭いピーク。±0.05 で素点が半減。固定テンポの検出に十分 |
| librosa の `beat_track` / `tempo` | **単体では使えない** | 99.384 を返し、剛体グリッドからの平均ズレ 41.6ms。候補列も 95.7/99.4/103.4 とバラける |
| 小節頭の同定 | **使える** | キック(低域)＋スネア(中域)の位相スコアで一意に決まり、クラップが2・4に乗ることで裏取りできた |
| キー検出（K-K プロファイル） | **使える** | ♭5つ。**ベースの音名分布の上位7音がスケールと完全一致**して独立に裏が取れた |
| コード進行 | **使える（骨格のみ）** | ループ長で畳んでから当てると、6分割の piano/guitar/other が独立に同じ4小節進行を出した |
| コードの細部（9th/sus/転回） | **使えない** | chroma のにじみで隣接音が分離できず、同じ小節が maj9/maj7/sus4 に揺れる |
| ステム分離（4分割） | **使える** | 加算残差 -20.3dB |
| ステム分離（6分割） | **条件つき** | 加算残差 -14.6dB。piano/guitar/other に割る際に 2.5dB 取りこぼす。**合議には有用、音として使うなら4分割** |
| ドラムの16分プロファイル（中高域） | **使える** | クラップ 2拍=100 / 4拍=79 と綺麗に立つ。マイクロタイミングも ±6ms で読めた |
| ドラムの16分プロファイル（低域） | **使えない** | 帯域通過の時間分解能が原理的に足りず1〜2個ぶん滲む。**拍単位までに落とす** |
| スウィング量 | **使える** | 0.4991（ハネ無し）を出せた。8分裏 vs 表の平均ズレで測る方式 |
| ベースのピッチ（pyin） | **条件つき** | オクターブ誤検出で min/max が26半音に膨らむ。長さ重みの 5-95% 区間なら 18半音で実態に近い |
| basic-pitch | **統計用なら使える / 譜面には使えない** | コード構成音率 0.78-0.85・グリッド±30ms内 0.70-0.84。ただし**持続音を刻む**（1小節伸びる和音が20音/小節） |

### 実装で踏んだ落とし穴（次の曲でも効く）

1. **BPM の粗探索を全長でやると正解が谷になる**。BPM が Δ ずれたグリッドは終端で `span×Δ/bpm` 秒歩く。
   230秒・97BPM だと 0.25BPM 刻みで 1/3拍ぶん歩き、**97.6 を外して 122.0 を返した**。
   → 曲の中ほど45秒で候補を出し、全長で精密化する2段構成にした
2. **探索レンジを広く取ると倍テンポに負ける**。HIPHOP の8分ハットは4分のキック/スネアと同程度にオンセットが立つので、
   60-200 で探すと 195.2（= 97.6×2）が僅差で勝つ。→ 70-150 に絞り、半分/倍の素点も JSON に残して検算可能にした
3. **オンセット強度に STFT ベース（`librosa.onset.onset_strength`）を使うと低域が鈍る**。
   帯域通過 → 振幅包絡 → 立ち上がり、のサンプル解像度方式に変えたら16分プロファイルが読めるようになった
4. **アタック時間を STFT の hop（23ms）で測ると全ステム同じ値になる**（実測で全部 325.1ms に張り付いた）。
   サンプル解像度の包絡で「ピークの10%からピークまで」を測る方式にしたら 31ms(piano) / 114ms(guitar) と分離した
5. **小節に畳んだプロファイルを floor でビン分けすると、グリッドから少し早いだけの音が1つ前のビンに落ちる**。
   「全部が .75 の位置にある＝38ms ずれている」と誤読した（実際のズレは17ms）。round で丸める
6. **コードテンプレートに m7♭5 を入れないと dim に化ける**。マイナーキーの iiø が全部 dim になり、
   「なぜか減和音だらけの曲」という誤読になった
7. **ハット帯域にはクラップのアタックが混入する**（クラップは広帯域）。分離できないので前提として書く
8. **matplotlib の図タイトルに日本語を入れると豆腐になる**（フォントが無い）。図中は ASCII に統一し、
   説明は Markdown 側に書く
9. **ffmpeg で `-ss`/`-to` を `-i` の後ろに置くと、`-af` のフィルタは入力側のタイムスタンプを見る**。
   `afade=t=out:st=<クリップ内の秒>` が「とっくに過ぎた時刻」と解釈され、**クリップ全体が無音になる**
   （切り出し18本中14本が無音のままレビュー依頼に出た）。曲頭付近のクリップだけ偶然無事だったので気づきにくい。
   短い切り出しは soundfile の部分読み＋サンプル単位のフェードで済ませる方が取り違えようがない
10. **音声を書き出したら、長さでなく RMS/peak を見る**。9 のバグは「ファイルがある・長さが正しい」を
   確認して pass にしていたため素通りした。`excerpts.py` は自分の出力の RMS を出し、無音があれば
   非ゼロ終了するようにした
11. **「鳴っているが小さい区間」を"一番小さい小節"で選ぶと、その楽器が休んでいる区間（-60dB）を掴む**。
   聴いても何も分からないクリップになるので、ピーク -18dB に**一番近い**小節を選ぶ。
   休符区間の残留音量は数値（`floor_below_peak_db`）で見れば足り、クリップにする必要はない

### 言えること / 次

- **Phase 1 の制約カードに載せてよいのは**: BPM・キー・ループ長・コードの「性格」（7thの有無・動かない小節の有無・ルートの方向）・
  スウィング量・クオンタイズ度合い・16分ごとの出現率（低域は拍単位）・ベースの音数/音域/音価・編成の在不在と8小節単位の構成。
  **載せてはいけないのは**: コードの細かい種別、キックの16分位置、basic-pitch の音価
- 分析の重心は「上モノが技術的に一番不確か」という事前の読み通りだったが、**不確かなのは音高でなくリズム側の粒度**だった。
  和音の骨格はループ畳み込みで十分取れる
- demucs が15秒で終わるので、**曲を増やすコストは実質ゼロ**。ライブラリ蓄積は当初想定より速く回せる
- 次の曲では `analyze.sh` 一発で回るところまで自動化済み。トリム位置の判断だけ手動

## 2026-08-03（追記） demucs は同じ入力でも同じステムを出さない

- **対象曲**: 同上（RAU DEF - FREEZE!!!）
- **やったこと**: 「ステムはいつでも再生成できるから消してよいか」を判断するため、同じ `track.wav` に
  `htdemucs`（`-d mps`）をもう一度かけて、既存のステムと突き合わせた
- **結果（実測）**:

  ```
  stem       md5      差のRMS   ステム比    重心(旧→新)        mid帯域比(旧→新)
  drums      不一致   -39.0dB   -24.9dB   2443.2 → 2460.4Hz   0.1803 → 0.1803
  bass       不一致   -38.1dB   -14.6dB   1894.0 → 1960.3Hz   0.3274 → 0.3228
  other      不一致   -36.9dB   -17.1dB   1240.1 → 1234.0Hz   0.6465 → 0.6445
  vocals     不一致   -40.9dB   -22.7dB   2364.1 → 2363.2Hz   0.4294 → 0.4287
  ```

  差はステム比 -15〜-25dB で、**数値誤差（-80dB級）ではなく実際に違う音**。
  MPS（GPU）の演算順序が固定でないためと思われる（CPU 実行での再検証は未実施）。
  派生する統計は 0.5〜3.5% しか動かないが、レポートに書いた「1240Hz」が再生成後は「1234Hz」になる。

- **言えること / 次**:
  - **ステムは「いつでも同じものを作り直せる中間生成物」ではない。消すとレポートの数値が再検証できなくなる**
  - 消してよいのは決定的に再生成できる派生物だけ: `source.wav`（`track.wav` があれば用済み）と
    `analysis/click.wav` / `midi_check-*.wav`（全長だが聴くのは `listen/` の抜粋のみ）。計164MB／636MB
  - 容量そのものは問題ではなかった（636MB×20曲=12.7GB に対し空き244GB）。**存在しない問題を最適化しかけた**
  - 分析の数値を報告する前に「その入力は再現できるのか」を先に確かめる。再現できないなら入力を残す

## 2026-08-03（追記2） 2曲目で3つ壊れた — 上モノの無い曲・遅い曲・ハットの無い曲

- **対象曲**: kzm - どしゃぶり feat. JUMADIBA（73.006 BPM / F minor / 48小節 / 2:38）。
  1曲目と正反対の性格で、**ドラム＋ベース＋声だけ**・上モノがほぼ無い
- **やったこと**: `add.sh` で取得〜分析まで通し、そのまま `excerpts.py` が落ちた
- **結果（実測）**:

  1. **`excerpts.py` がクラッシュ**（`zero-size array to reduction`）。曲尾のクリック範囲を
     「77-92小節」と決め打ちしていたが、この曲は48小節しかなく、範囲外を切って0バイトのファイルを書いていた。
     → 小節数を `track.wav` の長さから導き、`cut()` は範囲が外に出たら書かずに False を返すよう修正
  2. **上モノが無いのにコード進行が出た。** ステムのミックス比が piano -68.8dB / guitar -40.6dB /
     other -33.1dB（1曲目は -16〜-18dB）。それでも4つの上モノ全部が `Fmaj9` で一致した。
     **「3ステムが独立に一致したら信用してよい」は、全部が同じかぶりノイズを見ている場合に成立しない。**
     → `topline.py` に `chord_estimate_usable`（ミックス比 -25dB 未満で false）を追加。
     `excerpts.py` はコードの出どころを決め打ちにせず、使えるステムのうち一番大きいものを選ぶ
  3. **スウィングが 0.3849**。0.5 を下回る＝裏拍が表より94ms早い、で音楽的にありえない。
     ハットの無い曲で高域が別の音（歪んだ808等）を拾っている。
     → `groove.json` に `swing.plausible`（0.45-0.80 の外で false）を追加

- **言えること / 次**:
  - **2曲目で3つ見つかった**。1曲だけで書式と閾値を固めなくてよかった。素直でない曲を選ぶ価値が実証された
  - 共通する失敗の形は「**入力が想定外でも何かしらの数値を返し、壊れたことを申告しない**」。
    どの分析にも「この入力で意味のある数値か」の判定を付け、レポート側はそれを先に見る
  - `chord_estimate_usable` の -25dB は2曲の実測（-16〜-18 vs -33〜-69）で引いた線。曲数が増えたら見直す
  - 次に試すなら「テンポが揺れる曲」「途中でループが変わる曲」。まだ壊し方が分かっていない

## 2026-08-03（追記3） BPM のオクターブ判定が構造的に間違っていた／レポート生成を1コマンド化

**訂正**: 追記2で「kzm - どしゃぶり = 73.006 BPM / 48小節」と書いたが**間違い**。正しくは
**146.012 BPM / 97小節**。追記2で報告した上モノとハットの件は、この修正後も有効。

### BPM のオクターブ

- **症状**: 2曲目のグルーヴが読めなかった。低域が全16分にほぼ均等（77〜100）、mid が隣接スロット
  3-4 と 11-12 の両方で最大。小節に畳むと**スネアもハットも「小節の半分」で同じ形が繰り返していた**
- **原因**: 剛体グリッドの素点は**常に遅い方を好む**（遅いグリッドは強い点だけを拾うため）。実測で
  `half 36.5=0.319 > x1 73.0=0.296 > double 146.0=0.239` と単調に減っていた。
  探索レンジ（70-150）で抑えていたが、**73 と 146 が両方レンジ内に入る曲では効かない**。
  1曲目が通っていたのは 195.2 と 48.8 がレンジ外だったという偶然
- **対処**: 人が速さを感じる帯域（120 BPM 前後、σ=0.8オクターブ）の事前分布を素点に掛けて決める。
  レンジは事前分布が効くので 60-200 に戻した

  ```
  1曲目  x1=97.6(素点0.296→重み0.276)  double=195.2(0.261→0.177)  → 97.6 維持
  2曲目  x1=73.0(素点0.296→重み0.198)  double=146.0(0.239→0.225)  → 146.0 に修正
  ```

- **修正後**: mid が 80/79/100/93 と立ち、間が 2〜9 に落ちた（73のときは間が35〜69で埋まっていた）。
  スウィング 0.385（ありえない値）→ 0.493、ベース 7.83音/小節 → 3.92、音価 0.54 → 1.07 と全部正常化

### そのほか

- `add.sh` を **`analyze-url.sh`** にリネームした（「何を add するのか」が名前から分からず、
  `analyze.sh` / `report.sh` と品詞も揃っていなかった）。以前のエントリの `add.sh` は現在の `analyze-url.sh`

### レポート生成（`report.sh`）

- `claude -p`（ヘッドレス）で `report.md` まで1コマンドにできた。所要10〜15分
- **最初の版は28ターン迷走して落ちた**。プロンプトが「ゲートを確認しろ」と指示したせいで、
  ヘッドレス側が判定を自分で再検証しに行き、`octave_check` を読めば済むところを DSP から
  再導出し、`basics.py` のソースまで読み始めた
- **対処**: 判定をパイプライン側に移した（`gates.py` → `analysis/gates.json`）。
  プロンプトは「**この判定を自分でやり直さない。分析スクリプトの中身は読まなくてよい**」に変更
- **言えること**: AIに作業を投げるとき、**判断材料を渡すと判断をやり直す**。判断済みの結論を渡す。
  ゲートをパイプラインの出力にしたのは、レポート生成の都合以前に、そもそも正しい設計だった
- 副産物として `gates.py` 実装中にキー判定式の誤りも発見。「上位7音と8番目の比」で見ていたが、
  音階外の音も1つは鳴る（Db major の曲で Cb が8位に 0.045）。「上位7音が全体の何割か」に変更

## 2026-08-03（追記4） 3曲目／レポート生成器が分析側のバグを見つけた

- **対象曲**: my-way（100.0 BPM / F# major / 124小節）。1曲目寄りの性格で上モノが実在する
- **やったこと**: `analyze-url.sh` → `report.sh` を通しで実行。**両方とも人手の介入なしで完走**
- **結果**:
  - レポート生成器が自分から「`arrangement.json` の `rms_db_mean` は音量として読めない」と申告し、
    ミックスの実RMSに差し替えて本文を書いた。**これは分析側の実バグだった**
  - 原因: セクションの音量を「全ステムの dB の算術平均」で出していた。dB は対数なので
    複数ステムを平均しても合成音の大きさにならず、さらに**鳴っていないステムの底に引っ張られる**。
    アカペラ区間が -76dB と出て「曲中で一番静か」に見えていた（実際は声だけで普通の音量）
  - → `arrange.py` は `basics.json` の小節ごとのミックスRMSを使うよう修正

- **この修正で1曲目のレポートの主張が2つ崩れた**（修正済み）:

  | 旧（バグ由来） | 新（実測） |
  |---|---|
  | 「入りの9dBの落差が引きを作っている」 | **4.3dB**（-14.2 → -9.9dB） |
  | 「ベースを抜いて戻すと10dB近く上がる」 | **0.5dB**（-10.4 → -9.9dB） |
  | 「一番大きいのはラップが終わったあと」 | 誤り。81-92 は -10.7dB で最大ではない |

  正しい姿は「**13小節目以降ミックスの音量は -9.4〜-12.0dB の2.6dB幅に収まり、山谷を音量で作っていない**」。
  エネルギー曲線は音量でなく**要素の数と帯域の占有**で作られている。マスターが強く潰されている
  （ピーク +0.4dBFS）ことの裏返しでもある。**元の数字の方が"良い話"に見えたのが危なかった**

- **言えること / 次**:
  - **レポート生成をAIに投げたことが、分析側のバグ発見につながった。** 数値を文章にする過程は
    「その数値は意味を成すか」を通るので、JSONを眺めるより異常に気づきやすい
  - dB を平均するときは対数であることを思い出す。合成音の大きさが欲しいならパワーで足すか、
    そもそもミックスを直接測る
  - 3曲とも人手の介入なしで完走した。パイプラインとしては回る状態になった

## 2026-08-04 4曲目（ライブ演奏）で tempo_stable ゲートが初めて実戦で発火した

- **対象曲**: Jinmenusagi - GOAT feat. Lunv Loyal（03-Performance | From Tokyo。**ライブパフォーマンス映像**）。

- **やったこと**: `ref:url` で取得〜分析。制約カード（この日実装した `card.py`）まで通しで実行
- **結果（実測）**:
  - `tempo_stable` が落ちた: `grid_contrast_by_eighth = [2.00, 1.08, 0.89, 0.95, 1.13, 1.01, 1.33, 1.16]`。
    曲頭は剛体グリッドが強く効く（2.0）のに、3〜4区間目でコントラストが 1.0 を割る＝グリッドが
    オフビート位置より弱い。`local_bpm_std 0.64`（71BPM スケール、約0.9%）
  - **「ドラムが無い区間のせい」ではない**ことを切り分け済み: 4分割 drums の小節RMSは
    全8区間で -21.8〜-24.5dB と均一に鳴っている。鳴っているのにグリッドが合わない＝実際の
    テンポ揺れ（生演奏）
  - card.json は**設計どおり生成されなかった**（「グリッドごと信用できない曲のカードは
    存在しないのが正しい」の初の実戦ケース。旧カード削除の経路も通った）
- **言えること / 次**:
  - 「テンポが揺れる曲で壊れる」は README の予告どおりだが、**壊れたことをゲートが申告して
    下流（カード）が黙って止まる**、という守りが実戦で機能した。2曲目までの「入力が想定外でも
    何かしらの数値を返す」問題への対策が効いている
  - パフォーマンス/ライブ映像はスタジオ音源と同名曲でもテンポ性質が別物。リファレンスに
    使うならスタジオ音源のURLを選ぶ
  - 揺れる曲を本気で分析したくなったら剛体グリッドでなくビートトラッキング追従が要るが、
    現状のスコープ（打ち込みHIPHOP）では優先度なし
