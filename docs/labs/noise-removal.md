### 結論

- **ノイズ除去機能は見送り**。現環境の録音チェーンはフロア約-80dBFSで、ソロでも聴感上問題にならず、
  ミックス中はマスキングで完全に埋まる。「聴こえないノイズを取る機能」は便益ゼロ
- 方式比較（Step 1: 古典 vs RoFormer vs DeepFilterNet3）は**未実施**。聴こえないノイズの素材では
  A/Bに判別力がないため（planのゲート取り決めどおり）

### 再評価の条件（これが変わったら測り直す）

- 部屋・マイク・インターフェース・ゲイン設定の変更
- スピーカーモニターでの録音（今回の事故で実測済み: オケ回り込みが無音部RMS -28.9dBFSに達し
  SNR 4dBまで悪化する。ただしこれはノイズ除去でなく**ヘッドフォンモニターで解決すべき問題**）
- オケが極端に薄い曲（マスキングが効かない・ソロ露出が長い構成）で気になったとき

### 副産物の知見（録音セットアップ）

- 録音が3回目で成立した2つの失敗はどちらも**ノイズ除去では救えない種類**だった:
  ①スピーカー回り込み（→ヘッドフォンモニター）②入力ゲイン過大のクリップ（クリップ率63.6%・
  歪みは後から除去不能。→声のピークが -12〜-6dBFS に収まるゲイン）
- mk5 の Phones 端子はデフォルトで Main 1-2 Mix のミラー。Phones Source を Phones Mix (L-R) に
  変えると「LaLa→ヘッドフォンのみ・スピーカー無音」が設定切替なしで成立する（恒久変更済み）
- 実測ツール: `tools/noiselab/measure.py`（フロアRMS・帯域分布・ハム検出・最静区間）。
  録音環境を変えたときのチェックに再利用できる

## 2026-08-18 追記 — 学習比較: 無処理 vs 古典（ブラインド3すくみ）

Step 0 終了後、本人の希望で実施（採用判定ではない）。`tools/noiselab/step1_classic.py`・
noisereduce 3.0.3 stationary・prop_decrease 1.0・声区間ゲイン一致・ラグ0確認済み。
素材ごとに X/Y/Z = 無処理／古典・理想条件（プロファイル=頭の無音）／古典・製品条件
（プロファイル=最静区間の自動検出）をランダム割当。

**結果（ブラインドで全問正解）**:

- 「明確に変」「ちょっと変」と指摘された2つ = どちらも**古典・製品条件**。連続フローの
  テイクでは自動検出プロファイルに声が混入し（RMS -36〜-39dBFS）、声そのものを引き算していた。
  除去音の増幅量が rap で**+3.7dB**しか要らなかった（= ほぼ聴こえるレベルの声を削っていた）のが物証
- **理想条件の古典も無処理に負けた**（「無処理の方が伸びやか」）。きれいなプロファイルでも
  ブレス・空気感・余韻を薄く削る
- ノイズの減少への言及はゼロ（聴こえないノイズは減っても聴こえない）

**結論の補強**: 現環境では「便益ゼロ（ノイズは元々聴こえない）・コストは知覚可能（声の質感が痩せる）」。
見送りは正しかった。加えて、**古典方式を製品に載せるなら「最静区間の自動検出」は隙間のない
テイクで声を食う**ことが実地で確認された — 将来再評価する場合、プロファイル取得方法は
設計をやり直すこと（この罠は plan の想定どおりだが、聴感での破綻の大きさは想定以上）。

副産物の学び: 単体試聴で気にならない差もA/B比較では明確に分かる（比較試聴の感度）。
処理の善し悪しは「除去音に声が混ざっていないか」を聴くのが最速の検査（RXの
output noise only と同じ運用）で、増幅量の数値だけでも異常検知できる。
