# コーパス対照分析の作法（2026-08-11 否定例10曲の対照で確定）

2つの集団（好き／そうでない、日本／海外、corpus／library）を比べるときに毎回踏む落とし穴。
分析を始める前に読む。実例は[対照分析レポート](../labs/reference-beat-contrast-analysis.md)。

## 1次元化に集団のラベルを使わない

「正例だけで決めた medoid からの距離」で軸を作ると、正例が近くなるのは構成上ほぼ自明。
ラベルを入れ替える permutation は medoid を固定したままなのでこのバイアスを補正できない。
実際に AUC 0.177 の「採用軸」が出た。**群の分離は role を一切見ない距離表の上で測る。**

同じ理由で、集団のラベルは feature にも距離計算にも渡さない。アーティスト名を feature へ
入れないのと同じ循環防止で、ラベルを反転しても距離表がバイト一致することをテストで固定する。

## 相関した軸への一律 BH は厳しすぎる

上モノの7軸が p≤0.06 に並ぶのに43軸一括 BH で全滅した。軸は独立でない
（明るさ↔上の伸び r=0.94、反復↔コード変化 r=-1.00）。

**同じシャッフルを全軸へ同時に当てる omnibus 検定**（統計量＝軸ごとの |AUC-0.5| の平均）なら
相関が null 側に入るので補正が要らない。ただし全 view へ同じ統計量・同じ有意水準を適用し、
結果を見てから基準を動かさない。

omnibus は「どの軸が効いているか」を答えない。特定には耳確認と交差ペアが要る。

## 軸を採用する前に交差ペアで halo を潰す

「正例側の曲 vs 否定例側の曲」の A/B だけでは、5軸連続で「好みの差」が出ても
(a) 5軸とも効いている と (b) 曲全体の印象が軸へ投影される halo を区別できない。

**軸の値と役割を食い違わせたペア**（否定例だが正例側の値の曲 対 正例だが否定例側の値の曲）で
値の側が選ばれて初めて、その軸が効いていると言える。

交差ペアに使う曲は、既に別の設問で聴いて印象が残っている曲を避けて組み直す。

## ステム単体の A/B は複雑な方を有利にする

ベース単体では「動く方がよく聞こえる」が「そのビートが好き」と一致しない。
単体で印象を掴んだら、必ず文脈（beat 全体）でも残るかを確認する。

それでも切り出せない軸は保留にし、境界としても「境界ではない」としても採用しない。
決着させるには**同一曲で1性質だけ動かす**比較（EQ で重心だけ、ループ長で反復だけ）が要る。

## 「差が見つからない」を「差が無い」と書かない

正例22対否定例10で43軸を検定する条件では、BH 通過に AUC 0.8 以上が必要だった
（通過3軸は 0.826・0.854・0.864、落ちた最小 p の軸が 0.759）。
中くらいの差（AUC 0.6〜0.75）はこの規模では検出できない。**検出力の下限を必ず併記する。**

測れなかった軸（confound で汚染されたもの）も「差が無い」ではなく「正しく測れていない」と書く。

## 集団の非対称を境界より先に監査する

集団間に測定条件の差（ボーカルの有無、マスタリング、音圧）があると、それが「好みの差」に化ける。
境界を1つも出す前に測る。

- **loudness 依存**: 同じ音へ gain をかけて再抽出。値が動く feature を列挙する。
  band_balance・centroid・rolloff・hpss・hit character・16分profile は不感、
  絶対 RMS だけが感応するのが正常。予想と食い違ったらそこにバグがある
- **混入感度**: 片方にしか無い成分（ボーカル等）を**もう片方へ実際に混ぜて分離し直し**、
  feature の移動量を測る。「その成分がある区間 vs 無い区間」の比較は区間の音楽的な差と混ざって
  使えない（曲間 IQR の2.7倍という物理的にありえない値が出て発覚し、方式変更後は0.49倍に落ちた）
- **区間選定バイアス**: 代表区間の選ばれ方が集団で系統的に違わないか。
  窓の音量差は音量不感な feature の値を壊さないので、これ単独では軸を落とさず注記に持ち回る

## grid を先に人手で確定させる

否定例6曲が grid `needs_review` となり、耳で確認したら4曲が「小節頭を3拍ぶん後ろへ」で一致した。
直さなければ片方の集団だけ小節頭が1拍ずれた状態で16分profileを比較し、
「ドラム配置が違う」という偽の境界が出ていた。

## 人間判断は機械の再実行で上書きしない

曲を足して再監査したら、前回の人間回答7曲分が機械判定へ戻った。
人間が答えた項目はスキップし、上書きは明示フラグでのみ許す。回答は再生成されない場所に置く。

## 確認手順を作る前に「本人がもう答えているか」を確かめる

否定例として選んだ曲を「否定例として妥当か」と聞き直す round を作ったが、
選定時点の情報を超えず無駄だった。しかも対照曲がインストだったため素材が元音源とほぼ同じだった。

## 相対時間だけで測ると知覚が落ちる

全 feature が小節基準（テンポを割り算で消している）だと、「細かく刻まれすぎ」「ゆったり」のような
**実時間の速さの知覚が構造的に見えない**。同じ16分の刻みでも 126BPM は 89BPM より毎秒の打点が4割多い。

実際、ある曲のハットは相対時間で32%tile（細かくない）、実時間で95%tile と評価が逆転した。
知覚に関わる問いでは、相対時間の軸と実時間の軸を両方持つ。

## 耳確認の順序

1. **view 全体**（その集団の典型2曲）で差があるかを先に決める
2. 差があったら**軸ごと**に分解する。全軸で「差がある」なら分解に失敗しているので交差ペアへ
3. **交差ペア**で halo を潰す
4. 決着しない軸は**値域の端**を並べて「この軸は何を測っているか」から確かめる

機械の判定（`distant_candidate` 等）は回答前に見せない。判断が引きずられて検証にならない。
