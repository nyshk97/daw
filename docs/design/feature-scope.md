# 機能の要否判断 — 制作スコープと判断軸

機能追加を提案・検討する前に必ず読む。「引き算が価値」を具体的な判断手続きに落としたもの。

## 制作スコープの3層

LaLa で実際に行う制作は3層（2026-07-24 に本人が明言）。機能の使用頻度を見積もるときは、この3層に照らして考える。

1. **ボーカル多重録音** — Tier 1 の主目的
2. **購入ビート・リファレンス楽曲の取り込み** — オーディオトランスポーズの動機
3. **「1.5階」= 自分でもある程度ビートメイクする** — MIDIトラック・ピアノロール・SynthBank の投資先。ただし音色・サウンドデザインを深くこだわるタイプではない

「ボーカル録音だけ」を前提にすると要否判断を誤る（3層目を落としてしまう）。一方、ビートメイクを含めてもなお不要なもの:

- **オートメーションは不要** — 曲の抑揚はアレンジ（リージョンの抜き差し）で作る前提。ただし**曲末フェードだけは専用機能として持つ**（一般形は作らない。理由と再検討の線引きは [region-settings.md](region-settings.md) の「オートメーションを持たない」節）
- **オーディオクオンタイズは永久に不要**
- ライザー / スウィープはサンプル素材で代替する
- ビートメイク由来で将来浮上しうるのは **サイドチェイン**（Tier 2 の Comp スライスの dig で要否判断する）

## 判断軸: 使用頻度 × 恒常的な複雑さの税金

機能提案は「使用頻度」×「恒常的な複雑さの税金」で判断する。**実装コストそのものより、次の2点を重く見る**:

- 今後追加する全機能が、その存在を考慮させられるか
- 滅多に通らないパスに複雑さが集中しないか

### 適用のしかた

- 機能案を出すときは、要求を**頻度で分解**する。低頻度の部分は軽い代替（別プロセス・手動運用・既存機能の組み合わせ等）に逃がす案を先に示す
- レビューでブロッカーが多発したら、設計ではなく**要求自体を疑う**

### 実例: マルチウィンドウ化の破棄（2026-07）

複数プロジェクトの同時オープン（アプリ内マルチウィンドウ）は、実装前レビューを通過した後に破棄した。年数回のニーズに対して、クロスウィンドウ協調（再生調停・サンプルレート競合・非同期ダイアログチェーン）の恒常コストが見合わないという判断。

必要になったら2プロセス方式（`moreThanOneInstanceAllowed` ＋ プロジェクトディレクトリのロックファイル）で実現する。
