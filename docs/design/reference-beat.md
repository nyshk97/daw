# リファレンス駆動ビートメイク（仮称）

2026-08-03 の壁打ちで骨格を確定。長期プロジェクトとして複数フェーズで回す。名前は未定（本人の畳語案が出たらファイル名ごとリネームする。中身の参照は相対リンクのみなのでリネームは安い）。

## ゴール（2本柱）

1. **作る** — リファレンス音源から「雰囲気は似ているがパクリではない」ビートを、**細かくガチャを回しながら**作る。全自動の一発生成はしない — 自動化するのは分析と候補生成まで、選ぶのは常に人間
2. **わかる** — そのビートが「なんでいいのか」を因果で言語化し、引き出しを増やす・自分の好みに気づく。分析データを人間可読のレポートにもレンダリングすることで実現する（同日の壁打ちで追加）

## 音楽的な分解 — 何を借りて、何を借りないか

「雰囲気」を運ぶ要素と「パクリ」と認識される要素は分かれており、借りて安全な側が雰囲気の大半を運ぶ。

**借りる（雰囲気を運び、著作権的にも安全側）**

- BPM・キー/モード
- ドラムのグルーヴの性格: パターン密度・スウィング量・ハイハットの刻み方
- 音色パレット（編成: どの系統の楽器の組み合わせか）
- コードループの性格: ループ長・明暗・動きの少なさ
- エネルギー曲線（構成のどこで抜き差しするか）

**借りない（パクリの本丸）**

- メロディ・トップライン・リフそのもの
- 音源そのままのサンプリング（原盤権の領域）

MIDIは「パターンそのもの」を借りず、**統計的な性格**（密度・スウィング・音域・リズムの偏り）だけを制約として借りる。「制約を抽出 → 制約の中でガチャ」という構造は、やりたいこと（似てるけど違う）と安全性が自然に一致する。

## 作らないもの

- **アプリ内の分析表示UI** — 楽器判別・分析そのものはパイプラインでやる（ガチャの制約とレポートの両方が使う）が、結果を LaLa の画面には出さない。出力は機械可読の制約カードと人間可読のレポート（Markdown・LaLaの外で読む）のみで、アプリの複雑さの税金はゼロに保つ
  - 線引きは「**画面に情報を増やすか、操作の結果を変えるか**」。前者は永久に画面と実装を占有するが、後者は一度効いたら消える。作らないのは前者（コード進行をタイムラインに描く・波形の上に楽器名を出す）で、後者（BPMをプロジェクトに設定する・検出した小節頭にリージョンをスナップする・ステムをトラックとして取り込む）は作ってよい
- **一発全自動「リファレンス→ビート完成」** — 研究プロジェクト化する上に「ガチャを細かく回したい」と正反対
- **ラップ補助** — 本プロジェクトのスコープ外。ビート→ラップの依存は一方向なので後発の別プロジェクトにする

## アーキテクチャ

- **分析・MIDI候補生成 = 外部Pythonパイプライン**（`SpawnedProcess` 経由。yt-dlp連携と同じ形）。ステム分離・キー/BPM検出・音声→MIDI変換はPythonエコシステムにしかなく、C++移植の税金が巨大。分析は曲ごとに1回の低頻度処理なので [feature-scope.md](feature-scope.md) の「低頻度は別プロセスへ」に合致
- **試聴・ガチャ操作・採用 = LaLa内**。候補MIDIは普通のMIDIリージョンとしてSynthBankで鳴らす。音を鳴らす仕事はPythonに持たせない（リアルタイム性の問題を最初から作らない）
- 分析の出力は**同じデータの2レンダリング**: 制約カード `analysis.json`（機械可読・ガチャの入力。BPM・キー・グルーヴ統計・編成）と**分析レポート**（Markdown・人間可読・言語化のための読み物）。LaLaとの受け渡しはファイルのみ（制約カード＋MIDI）
- リファレンスごとに1フォルダ（音源・ステム・制約カード・レポート）を蓄積する。「この曲がなぜいいか」は1曲で分かるが「自分が何を好きか」は複数曲の横断で初めて見えるため。ただし置き場は**プロジェクトフォルダの中**で、共有ライブラリは作らない（下記「決まったこと」）
- プラグイン（AU/VST）方式は不採用 — あれはリアルタイム信号加工の器で、オフライン生成には形が合わない

### UXの流れ

1. リファレンス取り込み（既存のURL取り込み / ファイルインポート）
2. リージョン右クリック→「リファレンスとして分析」→ 進捗オーバーレイ（URL取り込みと同じ）→ 制約カードがプロジェクトフォルダに落ちる
3. ガチャUIでパーツごとに振り直し。振り直し＝制約カード＋シード値でPython生成をspawn（ルールベース生成は軽いので体感一瞬）
4. 採用は特別な操作ではなく「気に入った候補を残してピアノロールで手直し」

## 分析レポートの書き方

- ラベル（「Rhodes＋808」）で終わらせず、CLAUDE.md の説明作法と同じルールで**因果で書く**。載せるのは: 編成・音色の質感が雰囲気にどう効いているか／グルーヴのどこがジャンルの定石でどこが逸脱か（曲の個性は大抵逸脱側にある）／構成のエネルギー曲線（どこで何を抜くか）
- レポートは目次・入口。ピンポイントの「なんで?」（この16小節目でゾクッとする理由、等）は事前生成できないので、残したステム・データを使った Claude Code との対話で深掘りする前提

### 節の順序（2026-08-03 に第1号を書き直して確定）

**雛形は [../../tools/reference/report-template.md](../../tools/reference/report-template.md)**（リポジトリ内）。
節の並びと、各節に何を書くか・どこが機械的に埋まりどこが判断かを、HTMLコメントで埋め込んである。
Phase 1 の `report.py` はこのファイルを入力にする。

大枠は「**曲の話 → `---` → 付録（ツールの話）**」で、曲の話は
`基本情報`（尺・BPM・キー・楽器編成・構成の要約）→ 各論（ハーモニー / グルーヴ / 音色と帯域 / 構成）
→ 「〈本人が使った言葉〉は何でできているか」。
付録は `分析の条件` / `実測データ` / `どこまで信じてよいか` / `耳で検算する`。

**この順序にした理由**（第1号の初稿がどれも守れておらず読みにくかった）

- **曲の話とツールの話を混ぜない。** トリムの説明・信頼度・レビュー依頼を本文に挟むと、読者の頭の切り替えが何度も起きる。付録に全部隔離する
- **冒頭は客観的事実のカードにする。** BPM・キー・ハネの有無・何の楽器が何系統・構成、を解釈抜きで置く。「結論」や「一言でいうと」から始めない — 知りたいことは1つではないので、まず事実を渡して読者に選ばせる
- **表は本文に置かず付録の「実測データ」へ。** 表は読むものでなく引くもの。本文の途中にあると流れが切れる。本文に置くのは主張の直接の根拠になる小さな表だけ
- **同じ主張を2回説明しない。** 各論で1回説明したことは、後の節では結論だけ参照する。繰り返すと「主張→根拠」の構造が「同じ話の再放送」に見える
- **見出しは結論にする。** 「グルーヴ」ではなく「グルーヴ — 完全に打ち込み。癖は2つだけ」。見出しだけ拾って要旨が追える状態にする
- 引用ブロック（`>`）は**「作るときにどう使うか」と「深掘りのフック」だけ**に使う。注意書きに使うと役割が混ざる

### 生成の分担

`report.md` は**スクリプトでは生成していない**（Phase 0 時点）。雛形の `【機】` は JSON からの転記で
埋まるが、`【判】`（どこが定石でどこが癖か・なぜそれが効くか）は**テンプレート化できない**。
全自動にすると数字の羅列になり価値が落ちる。

Phase 1 で `report.py` を作り、雛形の `【機】` を埋めた状態で出力する。`【判】` は見出しと
コメントだけ残し、Claude Code が JSON を読んで埋める。

埋まった実例: `~/Music/daw/references/rau-def-freeze/report.md`（Phase 0 の第1号）

## ガチャの操作モデル

- 一括再生成ではなく**パーツ単位の振り直し＋ロック**（ドラム固定でベースだけ振り直す、等）
- 生成順はドラム→ベース→コード/上モノ（土台が決まらないと上を評価できない）
- 生成方式は (a)ルールベース（スケール内・グルーヴテンプレート変形）＋ (b)パターン集からの借用＋変異 から始める。(c)生成モデルは実験の結果次第
- 音色ガチャはまず SynthBank（GM）の範囲で回し、「1.5階」の要求水準で足りるかを実地判定する

## 決まったこと（Phase 0 で確定）

- **Pythonパイプラインの置き場は `tools/reference/`**。venv は `.venv/`（gitignore・`setup.sh` で再構築）、Python は `.mise.toml` の `[tools]` で 3.12 に固定。使い方と設計上の注意は [../../tools/reference/README.md](../../tools/reference/README.md)
- **スクリプトは項目ごとに分ける**（1本にまとめない）。Phase 1 の制約カードは「信頼できた分析だけ載せる」方針なので、項目単位で差し替え・除外ができる粒度に保つ

### リファレンスの置き場は `<プロジェクト>/references/<リファレンス名>/`

共有ライブラリ（`~/Music/daw/references/` のような第2のルート）は**作らない**。LaLa は
`~/Music/daw/<プロジェクト>/` に全部入っている自己完結型なので、そこに揃える。

```
~/Music/daw/<プロジェクト>/
├── project.json
├── clip-NNN.wav
└── references/<リファレンス名>/
    ├── track.wav          分析対象（リージョンの範囲を書き出したもの）
    ├── stems/             htdemucs / htdemucs_6s
    ├── analysis/          制約カード(JSON)・図・MIDI
    ├── listen/            耳で検算する短いクリップ
    └── report.md
```

- 共有ライブラリにしない理由: 命名規則・同じ曲を2プロジェクトで分析したときの重複・プロジェクト削除後に残る孤児、を全部考える必要が出る。横断レビューは `~/Music/daw/*/references/*/report.md` の glob で足りるので、第2のルートを作る理由になっていない
- プロジェクトを消すとレポートも消えるが、`report.md` は20KBなので必要なら手でコピーすればよい。それが痛くなるまでライブラリは作らない
- **保存時のクリーンアップとは干渉しない**: `Project::save` の未参照WAV削除は非再帰かつ `clip-*.wav` / `instr-*.wav` 限定なので、`references/` 配下は消えない
- **ただしリファレンス音源そのものは消える**: 取り込んだ音源は `clip-NNN.wav` なので、タイムラインからリージョンを外して保存すると実ファイルが削除される。**分析時にリージョンの範囲を `references/<名前>/track.wav` へ書き出す**こと（パイプラインはもともとトリム済みの `track.wav` を要求するので、トリムの入力元が変わるだけ）。取得したままの `source.wav` は保持しない
- **MVエディットのトリム判断が人手から消える**のがこの経路の利点。リージョンの範囲がそのままトリムになるので、波形とスペクトログラムを目視して ffmpeg で切る手順が要らなくなる

### ステム分離は4分割と6分割の両方を走らせる

`htdemucs`（4分割）と `htdemucs_6s`（6分割）は別々に訓練された別モデルで、共通のはずの
drums/bass/vocals も出力が違う。どちらかが優れているのではなく**用途で逆になる**ので両方使う。

- **ベース・ドラムは4分割**。ベースの調波打楽器比が 10.4 に対し6分割は 5.14 で、打楽器成分が倍入る
  （キック混入とみられる）。ピッチ追跡とオンセット位置が狂う
- **上モノは6分割**。piano/guitar/other の3本に分かれるので、同じコード検出を3回かけて検算できる。
  4分割は上モノが `other` 1本で検算できず、実際にループ長を 8小節 と誤答した
  （4小節=0.898 vs 8小節=0.913 の僅差。6分割の3ステムは揃って4小節）

**片方に絞ってもエラーは出ず、静かに劣化する**。時間とディスクが2倍かかるが、
分析の信頼度を落とさずに削る方法は今のところ無い。詳細は
[../../tools/reference/README.md](../../tools/reference/README.md) の「ステム分離とは / なぜ4分割と6分割を両方使うのか」。

### レポートの読み方と、深掘りの入口（Phase 3 で入れる3項目）

リージョン右クリックに並べるのはこの3つ。どれも税金が小さく、「アプリ内の分析表示UIは作らない」とも
衝突しない（**開くだけで、描画も情報の常駐もしない**）。

| 項目 | 実装 |
|---|---|
| リファレンスとして分析 | `analyze.sh <フォルダ>` を `SpawnedProcess` で。進捗オーバーレイ |
| レポートを開く | `report.startAsProcess()` — 1行。既定のアプリ（Obsidian / VS Code 等）で開く |
| このリファレンスについて聞く | ターミナルを開いて、そのフォルダで Claude Code を起動する。数十行 |

**レポートをLaLaの中に描画するのは当面やらない。** JUCE 8.0.9 に Markdown レンダラは無く
（`markdown` の語はソース全体で LV2 SDK の RDF メタデータにしか出てこない）、`AttributedString` では
表が組めないので、実質 `WebBrowserComponent`（WKWebView）一択になる。恒常的に効くのは次の3点:

1. `juce_gui_extra` の追加が必要（`juce_audio_utils` の依存には**入っていない**）で、**WebKit.framework をリンク**する
2. WKWebView は別プロセスを起こすため、Hardened Runtime 下で追加の entitlement が要る場合がある。
   `scripts/build.sh` は Sparkle の XPC 群を inside-out で個別署名する込み入った構成なので、
   **リリースのたびに検証項目が1つ増える**（失敗は notarize まで行かないと分からない）
3. Markdown→HTML 変換器がレポートの書式に追従し続ける必要がある（表・HTMLコメント・相対リンクの base URL）

**判断が変わる条件**: レポートの書式が固まった上で（2〜3曲ぶん実際に読んだ上で）、
外部アプリに飛ぶのが作業の切れ目になると感じたら入れる。書式が動いている間に変換器を作ると二度手間になる。
`startAsProcess()` の1行は捨てても惜しくないので後戻りコストはゼロ。

### 深掘り対話の実装形態

レポートを読んで気になった箇所を AI に聞く経路。3案あり、**A から始めて、使うと分かったら C**。

- **A. ランチャー**（数十行）— 上の「このリファレンスについて聞く」。会話はターミナル。LaLa は AI 連携も
  APIキーも課金管理も持たない
- **B. フル自前** — Anthropic API を直接叩き、tool-use ループを C++ で実装する。**Claude Code のサブスクとは
  別に API 課金が発生する**ため不採用
- **C. アプリ内チャット＋Claude Code をバックエンド** — `claude -p --continue` を `SpawnedProcess` で叩き、
  結果を自前のペインに出す。APIキー・課金・ツール実行は Claude Code 側に乗るが、会話UIとプロセス配管は持つ。
  なお C は「表示UIは作らない」原則に対する**初めての例外**になる（会話は開いたときだけとはいえ恒久的な画面要素）

**判断が変わる条件**: A を数回使ってターミナルへの移動が障壁になった / 音をその場で鳴らしながら会話したくなった。

### 分析の実行時間

3:50 の曲で通し **約4分**（demucs は4分割・6分割とも MPS で15〜17秒。残りが基礎分析・グルーヴ・上モノ）。
4分割か6分割のどちらかに絞れば2分台。UXの流れの「進捗オーバーレイ」で待たせる設計として成立する。
