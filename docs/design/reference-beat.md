# リファレンス駆動ビートメイク（仮称）

2026-08-03 の壁打ちで骨格を確定。長期プロジェクトとして複数フェーズで回す。名前は未定（本人の畳語案が出たらファイル名ごとリネームする。中身の参照は相対リンクのみなのでリネームは安い）。

## ゴール（2本柱）

1. **作る** — リファレンス音源から「雰囲気は似ているがパクリではない」ビートを、**細かくガチャを回しながら**作る。全自動の一発生成はしない — 自動化するのは分析と候補生成まで、選ぶのは常に人間
2. **わかる** — そのビートが「なんでいいのか」を因果で言語化し、引き出しを増やす・自分の好みに気づく。分析データを人間可読のレポートにもレンダリングすることで実現する（同日の壁打ちで追加）

## 音楽的な分解 — 何を借りて、何を借りないか

「雰囲気」を運ぶ要素と「パクリ」と認識される要素は分かれており、借りて安全な側が雰囲気の大半を運ぶ。

**借りる（雰囲気を運び、著作権的にも安全側）**

- BPM・キー/モード
- ドラムのグルーヴの性格: パターン密度・スウィング量・ハイハットの刻み方
- 音色パレット（編成: どの系統の楽器の組み合わせか）
- コードループの性格: ループ長・明暗・動きの少なさ
- エネルギー曲線（構成のどこで抜き差しするか）

**借りない（パクリの本丸）**

- メロディ・トップライン・リフそのもの
- 音源そのままのサンプリング（原盤権の領域）

MIDIは「パターンそのもの」を借りず、**統計的な性格**（密度・スウィング・音域・リズムの偏り）だけを制約として借りる。「制約を抽出 → 制約の中でガチャ」という構造は、やりたいこと（似てるけど違う）と安全性が自然に一致する。

## 作らないもの

- **アプリ内の分析表示UI** — 楽器判別・分析そのものはパイプラインでやる（ガチャの制約とレポートの両方が使う）が、結果を LaLa の画面には出さない。出力は機械可読の制約カードと人間可読のレポートのみで、アプリの複雑さの恒常的なコストは最小に保つ
  - 線引きは「**画面に情報を増やすか、操作の結果を変えるか**」。前者は永久に画面と実装を占有するが、後者は一度効いたら消える。作らないのは前者（コード進行をタイムラインに描く・波形の上に楽器名を出す）で、後者（BPMをプロジェクトに設定する・検出した小節頭にリージョンをスナップする・ステムをトラックとして取り込む）は作ってよい
  - **例外第1号（2026-08-05 決定）: レポートの閲覧ウィンドウ**。実使用でアプリ跨ぎ（Obsidian / ターミナル）が認知的負荷になったため、開いたときだけ表示する別ウィンドウとして実装した（下記「レポートの読み方と、深掘りの入口」）。メイン画面には情報を常駐させないので、線引きの精神（画面を占有しない）は維持している
- **一発全自動「リファレンス→ビート完成」** — 研究プロジェクト化する上に「ガチャを細かく回したい」と正反対
- **ラップ補助** — 本プロジェクトのスコープ外。ビート→ラップの依存は一方向なので後発の別プロジェクトにする

## アーキテクチャ

- **分析・MIDI候補生成 = 外部Pythonパイプライン**（`SpawnedProcess` 経由。yt-dlp連携と同じ形）。ステム分離・キー/BPM検出・音声→MIDI変換はPythonエコシステムにしかなく、C++移植のコストが巨大。分析は曲ごとに1回の低頻度処理なので [feature-scope.md](feature-scope.md) の「低頻度は別プロセスへ」に合致
- **試聴・ガチャ操作・採用 = LaLa内**。候補MIDIは普通のMIDIリージョンとしてSynthBankで鳴らす。音を鳴らす仕事はPythonに持たせない（リアルタイム性の問題を最初から作らない）
- 分析の出力は**同じデータの2レンダリング**: 制約カード `card.json`（機械可読・ガチャの入力。BPM・キー・グルーヴ統計・編成）と**分析レポート**（Markdown・人間可読・言語化のための読み物）。LaLaとの受け渡しはファイルのみ（制約カード＋MIDI）
- リファレンスごとに1フォルダ（音源・ステム・制約カード・レポート）を蓄積する。「この曲がなぜいいか」は1曲で分かるが「自分が何を好きか」は複数曲の横断で初めて見えるため。ただし置き場は**プロジェクトフォルダの中**で、共有ライブラリは作らない（下記「決まったこと」）
- プラグイン（AU/VST）方式は不採用 — あれはリアルタイム信号加工の器で、オフライン生成には形が合わない

### UXの流れ

1. リファレンス取り込み（既存のURL取り込み / ファイルインポート）
2. リージョン右クリック→「リファレンスとして分析」→ 進捗オーバーレイ（URL取り込みと同じ）→ 制約カードがプロジェクトフォルダに落ちる
3. ガチャUIでパーツごとに振り直し。振り直し＝制約カード＋シード値でPython生成をspawn（ルールベース生成は軽いので体感一瞬）
4. 採用は特別な操作ではなく「気に入った候補を残してピアノロールで手直し」

## 分析レポートの書き方

- ラベル（「Rhodes＋808」）で終わらせず、CLAUDE.md の説明作法と同じルールで**因果で書く**。載せるのは: 編成・音色の質感が雰囲気にどう効いているか／グルーヴのどこがジャンルの定石でどこが逸脱か（曲の個性は大抵逸脱側にある）／構成のエネルギー曲線（どこで何を抜くか）
- レポートは目次・入口。ピンポイントの「なんで?」（この16小節目でゾクッとする理由、等）は事前生成できないので、残したステム・データを使った Claude Code との対話で深掘りする前提

### 節の順序（2026-08-03 に第1号を書き直して確定）

**雛形は [../../tools/reference/report-template.md](../../tools/reference/report-template.md)**（リポジトリ内）。
節の並びと、各節に何を書くか・どこが機械的に埋まりどこが判断かを、HTMLコメントで埋め込んである。
`report.py` がこのファイルを入力に、`【機】`（二重波括弧プレースホルダ）を充填したドラフトを出力する。
判定語（「ハネ無し」等）の線引きは report.py のコードが単一の真実の源（テストで固定。
変更時は labs に理由を残す）。

大枠は「**曲の話 → `---` → 付録（ツールの話）**」で、曲の話は
`基本情報`（尺・BPM・キー・楽器編成・構成の要約）→ 各論（ハーモニー / グルーヴ / 音色と帯域 / 構成）
→ 「〈本人が使った言葉〉は何でできているか」。
付録は `分析の条件` / `実測データ` / `どこまで信じてよいか` / `耳で検算する`。

**この順序にした理由**（第1号の初稿がどれも守れておらず読みにくかった）

- **曲の話とツールの話を混ぜない。** トリムの説明・信頼度・レビュー依頼を本文に挟むと、読者の頭の切り替えが何度も起きる。付録に全部隔離する
- **冒頭は客観的事実のカードにする。** BPM・キー・ハネの有無・何の楽器が何系統・構成、を解釈抜きで置く。「結論」や「一言でいうと」から始めない — 知りたいことは1つではないので、まず事実を渡して読者に選ばせる
- **表は本文に置かず付録の「実測データ」へ。** 表は読むものでなく引くもの。本文の途中にあると流れが切れる。本文に置くのは主張の直接の根拠になる小さな表だけ
- **同じ主張を2回説明しない。** 各論で1回説明したことは、後の節では結論だけ参照する。繰り返すと「主張→根拠」の構造が「同じ話の再放送」に見える
- **見出しは結論にする。** 「グルーヴ」ではなく「グルーヴ — 完全に打ち込み。癖は2つだけ」。見出しだけ拾って要旨が追える状態にする
- 引用ブロック（`>`）は**「作るときにどう使うか」と「深掘りのフック」だけ**に使う。注意書きに使うと役割が混ざる

### 生成の分担（2026-08-06 実装。plan: `docs/plans/2026-08-05-1858`）

`【機】`（数値の転記・表・判定語）は `report.py fill` が analysis/*.json から機械充填する。
`【判】`（どこが定石でどこが癖か・なぜそれが効くか）は**テンプレート化できない**ので、
Claude Code（`report.sh` が Opus 5 固定で呼ぶ）がドラフトの【判】マーカーの内側だけを書く。
全自動にすると数字の羅列になり価値が落ち、全部 AI に任せると転記ミスと目盛りの揺れが混ざる —
その中間で線を引いた形。

- AI は gates.json もテンプレも読まない。ゲート判定はドラフトに焼き込み済み、
  【判】に必要な値はダイジェスト（report.py が同時生成）をプロンプトに同梱して渡す
  （「判断材料を渡すと判断をやり直す」の再発防止と、読みターンの削減を兼ねる）
- 書き終わりは `report.py check` の完成検査（プレースホルダ残存・必須見出し・
  各【判】マーカー内の実質執筆）を通ったときだけ report.md に昇格する

埋まった実例: `~/Music/daw/references/rau-def-freeze/report.md`（Phase 0 の第1号）

## ガチャの操作モデル

- 一括再生成ではなく**パーツ単位の振り直し＋ロック**（ドラム固定でベースだけ振り直す、等）
- 生成順はドラム→ベース→コード/上モノ（土台が決まらないと上を評価できない）<br>→ 2026-08-07 上モノのループ転換（下記「音色の調達」）に伴い、**ループ先行（雰囲気のアンカー）→ドラム・808→ベースはループ追従**へ逆転。「土台から積む」は生成物を評価する順序としての決定だったので、上モノが検索（完成品）になった時点で根拠ごと入れ替わる
- 生成方式は (a)ルールベース（スケール内・グルーヴテンプレート変形）＋ (b)パターン集からの借用＋変異 から始める。(c)生成モデルは実験の結果次第
- 音色ガチャはまず SynthBank（GM）の範囲で回し、「1.5階」の要求水準で足りるかを実地判定する<br>→ 2026-08-06 実地判定: **ドラム・808 は GM では足りない**（キットの質感がジャンル外）。差し替えはワンショットサンプラー1実装で賄う（[issue #3](https://github.com/nyshk97/daw/issues/3)・下記「Phase 2 の残りの着手順」）。上モノ鍵盤系は当面 GM で足りる

### Phase 2 の残りの着手順（2026-08-06 確定）: ベース → 音色 → 上モノ

issue: [ベースガチャ #2](https://github.com/nyshk97/daw/issues/2) / [ワンショットサンプラー #3](https://github.com/nyshk97/daw/issues/3) / [上モノガチャ #4](https://github.com/nyshk97/daw/issues/4)。各 issue はゴール・含めないもの・開いた論点のみを持ち、設計は着手時に /dig → /plot で詰める。<br>→ 2026-08-07 Phase 2 の残りは [ループ先行トラック #5](https://github.com/nyshk97/daw/issues/5) に一本化（#3 は吸収・#4 は保留棚ごと統合してクローズ）

- **ベースが音色より先**: トラップ系ではキックと 808 が同じ低域を分担して1つのグルーヴを作る。808 のサステインが隙間を埋める前提のキックパターンは単体だとスカスカに聞こえるため、ドラム単体の選別は「808 が乗れば正解だったパターン」を落とす。ドラム＋ベースが揃って初めてガチャの評価が当てになる
- **音色がベースの後**: キックの音色は単体の格好良さでなく 808 との帯域分担で選ぶもの（808 が低域を長く占有するならキックはアタックだけの短い音、等）。ベース確定前にキットを選んでも選び直しになる
- **808 = ピッチ付きワンショットサンプラー**: ドラムキットのユーザーサンプル読み込みと同一機構なので、「ドラムの音色」と「808 の音色」は1実装で潰せる
- **上モノは最後・GM で開始**: 生成順（土台→上）どおり。GM の弱点はドラム・808 に集中しており、鍵盤系はパターン評価に足りる<br>→ 2026-08-07 上モノは MIDI 生成でなく**ループ素材の検索を主経路**に転換（issue #4 はフォールバックとして保留降格。下記「音色の調達」）
- 順序を入れ替えてよい唯一の理由はモチベーション（GM の音でガチャを回す気になれない場合）。その場合もキット選びは仮決めと割り切り、ベース後に選び直す

**好みの境界を調べるときは近接した否定例を使う。** 好きな曲だけの正例コーパスは、好みの範囲や
連続性は示せても、「何が作りたい方向を分けるか」は特定できない。制作条件へ落とす分析では、
ジャンル・BPM・完成度が近い「良いが自分ではこの方向を作りたくない」曲を対照群にする。
明らかに遠いジャンルは使わず、音圧、配信品質、ボーカルの有無を好みの差として学習しないよう揃える。

### 上モノ素材の好みの境界（2026-08-11 対照分析で確定）

好きな23曲と「良いが自分の作りたい方向ではない」市販ビート10曲の対照から、**耳と統計の両方を
通った条件は上モノの2軸だけ**だった。ループ検索・推薦はこのレンジへ寄せる。閾値で切らず、
連続的な目標帯として扱う。

| 軸 | 目標帯（好き側 p10–p90） | 避ける方向（否定例 p10–p90） |
|---|---|---|
| 明るさ（spectral centroid） | 519–1397 Hz（中央値 871） | 382–833 Hz |
| コードの動き（root変化率） | 0.60–0.94（中央値 0.72） | 0.46–0.80 |

- ロールオフ95%は明るさとほぼ同一指標（r=0.94）なので、片方だけ制約すれば足りる
- 反復度は `1 - root変化率` の写し（r=-1.00）なので別軸として扱わない
- 粒立ち（倍音/打撃比の低さ）は弱い傾向どまりで制約にしない
- **「ラップの余白」は好みの境界ではない**（AUC 0.496）。条件に入れない
- ドラム配置・ドラム音響・曲全体の構成も境界として立たなかった。ガチャで自由に振ってよい
- ベースはview距離で最も強く分離するが、どの性質かは特定できていない。方向を持った条件にしない

根拠と限界は[対照分析レポート](../labs/reference-beat-contrast-analysis.md)。
重なりは0.42〜0.57と大きく、この2軸で好き嫌いを判定できるわけではない。
「素材を選ぶときにどちらへ寄せるか」の指針として使う。

### 音色の調達 — 3本立てと上モノのループ転換（2026-08-07 壁打ちで確定）

音色への投資は「加工・作り込み」ではなく**選択**（候補の質 × 比べやすさ）に集中する。
シンセエンジンやプラグインホスティング（Omnisphere 等）は不採用 — 音色がプラグインの中に
しか存在せず外からファイルとして扱えないうえ、ホスティングの恒常的なコスト（ウィンドウ・状態保存・
クラッシュ隔離）が以後の全機能に及ぶため。音色はすべて「ファイル」で持つ。

- **ワンショット（wav＋ピッチ再生）**: キック・スネア・ハット＋808/サブ系ベース（issue #3）。
  808 がワンショットで成立するのは、実体がほぼサイン波でフォルマントが無く、ピッチ変更の
  副作用（体格のずれ）が原理的に出ないため。倍音とアタックが命のピアノ・ギターは±2〜3半音が
  限界で、この経路には乗らない
- **ループ素材（オーディオ）**: 上モノ全部（鍵盤・ギターとも）。**上モノの MIDI 生成はやめ、
  ループ検索を主経路にする**。理由: ①ギターらしさは奏法（スライド・ミュート・ストロークの
  揺れ）に宿り MIDI では運べない ②ループは演奏・ミックス済みで完成度の天井が高い
  ③チョップは本人の主戦場のスキル（「買ったビートを切り直す」の細粒度版）。
  既存のオーディオリージョンで今日から敷ける — 新しい再生機構は不要
- **SFZ マルチサンプル（鍵盤系）**: 廃止でなく**保留**。ループ経路が細る場面（キー/BPM の合う
  ループが無い・ライブラリが薄い初期）のフォールバック。issue #4（GM 鍵盤ガチャ）も同じ
  位置づけに降格。使わないと分かったら「知った上で消す」

**最終形のフロー（2026-08-07 確定・ここへ向けて逆算する）**:

1. リファレンスを分析（既存: card.json＋report.md）
2. **上モノのループをおすすめ5から選ぶ**（検索ガチャ）→ 採用ループのキー/BPMをプロジェクトへ逆コピー
3. カード＋採用ループを制約に、**ドラム・ベース・808 の MIDI を生成ガチャ**（ベースはループ追従）
4. **各パーツの音色（キック・スネア・ハット・808 のワンショット）もおすすめ5から選ぶ**

人間に残る操作は「5個から選ぶ」と「振り直す」だけ。候補作りは全部機械側 —
「自動化するのは分析と候補生成まで、選ぶのは常に人間」のゴールそのまま。

**ガチャの一般形は変わらない**: 制約カード → 候補を並べる → 人間が選ぶ。候補の出どころが
**生成**（ドラム・808）か**検索**（ループ: プロジェクトのキー/BPM でフィルタ＋リファレンスの
ステムと質感が近い順）かはパーツごとの配管の違いで、UX（パーツタブ・振り直し・ロック・試聴）は
同一。市販ループはファイル名にキー/BPM を含む慣習があるため、検索側のインデックスは
ワンショットより安く作れる。

**ベースはループ追従モード**: ループが進行とキーを決めるため、ベースガチャの音高は
「カードから進行を生成」でなく「採用ループの実進行に従う」が主経路になる。実装は
パイプラインのコード検出を採用ループに向けてルート列を渡すだけ（「原曲進行モード」と
同機構・向き先違い。8小節のループなら分析は数秒）。

**帰結として浮上した将来の恒常的なコスト（意図して買う）**:

- **タイムストレッチ**（音程を変えずに長さだけ変える。Logic の Flex Time 相当）がほぼ確定。
  キーのズレはトランスポーズ±2〜3半音で逃げられるが、BPM は 1 でもズレるとグリッドに
  噛まない。用途は±10%程度の近距離救済（変化量に比例して濁る。持続音は綺麗に伸び、
  鋭いアタック連続は滲む — ドラムは生成側なので主対象は伸びに強いメロディループ）。
  自作せずライブラリ組み込み（signalsmith-stretch 等 — ライセンス・品質は着手時に裏取り）
- **選択体験への投資**: ループ再生中の**差し替え試聴**を issue #3 の中核に置く（音色の
  良し悪しは半分以上「他パートとの帯域分担」で決まるため、単体試聴で選ばない）。
  **おすすめ5**（分析済みの帯域重心・音色統計とライブラリの近傍探索。`tools/library/` の
  低頻度別プロセス）は、手動選びの面倒が実地で証明されてから

**おすすめ5の方式（2026-08-07 追記）**: 2段構え — ①ハードフィルタ（キー±2半音の
トランスポーズ圏内・BPM±10%のストレッチ圏内）で「使えるか」を足切り → ②生存者を
リファレンスの該当ステムとの類似（帯域重心・オンセット密度・帯域バランス・アタック）で
ランキング。特徴量を解釈可能なものに限るのは「重心が近い・明暗が同じ」と理由を一行
添えるため（選ぶ行為を「わかる」に繋げる）。並びが鈍いと感じたら音声埋め込み（CLAP系）へ
載せ替える道はあるが、理由の説明可能性を失うトレードオフ。
候補列は**1曲1枠**（2026-08-08 追記）: 同曲のテイク番号・質感違い（`_1`〜`_5`・`_LOFI`）を
ファイル名から同定して距離最小の1本に集約する。パックの実効曲数はファイル数より大幅に
少ないことがあり（APS ギターパックは160ファイル＝32曲）、集約しないと同曲が枠を占領する。

**調達はレコメンド前提で買い切り中心**: エンジンはディスク上のファイルしか並べられない
（Splice等のクラウドカタログに自前の分析は走らせられない）。サブスクは「おすすめ5が
外れたとき1本探しに行く」穴埋め経路で、落とした wav は次のインデックス更新で合流する。

**規模の目安**（top 5 がフィルタ生存者の1割未満、ループの生存率2〜3割、で逆算した桁感）:

| カテゴリ | 検証に足りる最小 | 実用の最終形 |
|---|---|---|
| ワンショット（レーンごと） | 50〜100本 | 200〜500本 |
| ワンショット合計 | パック1〜2個（数百本） | 1000〜3000本 |
| メロディループ | 100〜200本 | 500〜1500本 |

最終形を超えて増やしても重複が増えるだけ（掘る沼＝Omnisphere の1万4千プリセットと同じ
認知コスト問題）。**レコメンドの検証は規模より対照群**: ジャンル外素材（メタルのギター・
EDMの硬いキック等）を2〜3割混ぜ、chill系リファレンスでそれらが下位に沈むかで
「並びが効いているか」を判定する（同系統だけだと正しさと偶然を判別できない）。
進め方は「小さく買う→エンジン→対照群で効きを確認→買い足す」— 大量購入後にエンジンが
鈍いと、ライブラリとエンジンのどちらが悪いか切り分けられなくなるため。

**ライブラリの可搬性（2026-08-07 確定）— アプリに同梱せず、iCloud Drive 同期で運ぶ**:

- Logic の「本体＋最低限の音／サウンドライブラリは後からDL」構造は、LaLa では
  **LaLa.app＋SynthBank(GM)（同梱の最低限）／`~/Music/daw/library/`（拡張）**が既に対応物。
  アプリ内ダウンロード機構は作らない（あれは数百万ユーザーに配るための仕組み。N=1 の
  マシン間可搬性はファイル同期で足りる）
- **市販サンプルをアプリ成果物に焼き込むのはライセンス違反**（royalty-free は素材のままの
  再配布を禁止しており、daw-releases の .app は公開配布物）。「本体は公開物・ライブラリは
  私物」の分離は重さ以前に権利の要請
- 実体は iCloud Drive（`~/Library/Mobile Documents/com~apple~CloudDocs/daw-library/`）に置き、
  `~/Music/daw/library` から symlink。`index.json` も同居させ、特徴量のマシン間再分析を不要にする
- **eviction 対策必須**: iCloud の「Macストレージを最適化」はローカル実体を `.icloud`
  プレースホルダに置き換えることがあり、試聴・プロジェクトオープンがダウンロード待ちで
  止まる。ライブラリフォルダに Finder の「ダウンロードを保持」を指定する。
  新マシンのセットアップは「iCloud ログイン → symlink → ダウンロードを保持」の3点
- 規模の見込み（最終形 3〜6GB 程度）は 2TB プランの誤差

ループのライブラリ置き場（プロジェクト側のコピー方針）・検索ガチャのタブ設計は、
実装着手時の /dig で詰める。ファイル名はリネームしない（`Am_140bpm` 等の埋め込み
メタデータがインデックスの主情報源）。

### ベースガチャ（2026-08-06 実装。plan: `docs/plans/2026-08-06-1809-bass-gacha.md`）

**23曲の横断耳確認による補足（2026-08-10）**: 好みのbassには「動く支え」と「反復する土台」の
2つの極があったが、曲群全体はその間も含む連続体だった。ジャンル／タイプ切替を増やさず、
`pitch motion`（音高がどれだけ動くか）と`repetition`（同じ低音形をどれだけ保つか）の連続制約として
カード→生成器へ渡す。リズムモチーフの反復とは別軸で、動く支えも2小節の音高モチーフ自体は反復してよい。

代表曲の公開クレジットからbass音源の入手経路までは確定できず、2極と自演奏／既存曲sample／素材loopの
対応も立証できなかった。この結果だけを理由に新しい音源経路は追加しない。両極とも既存の
上モノloop追従MIDI＋pitch付きone-shotを主経路にし、動く側は音程変化、土台側はroot滞在と音価を変える。
調査記録は[reference-beat-taste-production-research.md](../labs/reference-beat-taste-production-research.md)。

- **プロジェクトに「キー」状態を導入**（project.json v13・root 0..11＋major/minor・未設定可）。
  常設UIはヘッダーLCDの KEY セクション（BPM と同格の基本情報）。生成は常にプロジェクトのキーで
  行い、カードの `global.key` は分析完了ダイアログの「BPM とキーを設定」による**1回きりのコピー**
  でだけプロジェクトへ入る（コピー時にルート=声域・モード=平行調取り違えの保険、を変更できる）
- **音高はカード駆動で chill / トラップ両対応**: chords スライスがあれば loop_bars×slots_per_bar
  スロットのルート列（進行）を root_motion / root_changes_per_loop の性格に従ってガチャ。
  chords 無し・変化0なら**ルート連打へ自然に退化**する。ジャンルスイッチは生成器に持たせず、
  リファレンス選びがジャンルを決める
- **パネルはパーツ切り替え型**（上部に Drums / Bass タブ。将来 Keys 等が +1 されるだけ）。
  候補リスト・カード参照・ロック（bass は進行/リズムの2軸）はパーツごとに独立 —
  ドラムは曲A・ベースは曲B、のパーツ別カード参照が成立する
- **仮配置はパーツごとに同時保持**（GachaSession のパーツ一般化）。baseline はセッション全体で
  1回・「残す」は全パーツ一括で undo 1件。パーツのカード変更はそのパーツだけ撤去する
- **リズムはモチーフ反復（2026-08-08 v5）**: リズムの型は偶数ループ=2小節・奇数=1小節の
  モチーフを1回サンプリングして繰り返し、進行（音高）だけが全ループ周期を追従する。
  ハーモニー周期とリズム周期は別物 — 16小節ループのアンカーで全小節が独立ランダムになり
  「型の反復が無い＝ヨレて聞こえる」実害が出たための分離。本数の確率的丸めもモチーフ全体で
  1回（小節ごとだと疎カードの密度が反復で倍増する）
- **キック噛み合わせ**: 配置済みドラムリージョン（仮配置優先→選択中 Drum Kit リージョン）から
  実ノート位置を抽出して `--kick-ticks` で渡す。同時打ちに選ばれたスロットはキックの実 tick へ
  スナップ。それ以外はグリッド正位置（swing・ジッターとも掛けない — カードの
  bass.quantize_dev_ms は低域オンセット検出の誤差で膨らむ疑いが強く、無相関ランダムの
  揺れはグルーヴでなくヨレに聞こえた実聴の結果）。試聴長 = max(ドラム長, loop_bars) で、短い側が seed 持ちガチャ産なら --bars 変更で
  延長再生成する
- **原曲と同時再生での音程評価はしない（2026-08-07 実聴で確定）**: 生成ベースはスケール内だが
  進行はガチャ（実進行は借りない設計）なので、原曲と重ねると生成ルートが原曲のコードと違う
  瞬間にぶつかる — これは設計の帰結であってバグではない。原曲の役割は BPM・キー・性格の供給と
  グルーヴのA/B参照（ドラム＝音程なしのパーツ）まで。ハーモニーの評価は原曲をミュートして
  生成物同士で行う。再検討のタイミングは**上モノガチャまで作り終えて
  「原曲に雰囲気が似ない」と感じたとき**（2026-08-07 決定）。そのときはカードに実ルート列を
  載せる「原曲進行モード」（オプトイン）を検討する — 実進行は analysis/ に残っているので
  後付けのコストは小さい。なおコード進行の借用はパクリ感のブロッカーではない（「同じ曲」と
  認識させる主犯はトップライン。進行はありふれた共有部品で、一致が危険になるのは
  珍しい進行＋同キー＋同BPM＋同音色＋似たトップラインと軸が積み重なったとき）

## 決まったこと（Phase 0 で確定）

- **Pythonパイプラインの置き場は `tools/reference/`**。venv は `.venv/`（gitignore・`setup.sh` で再構築）、Python は `.mise.toml` の `[tools]` で 3.12 に固定。使い方と設計上の注意は [../../tools/reference/README.md](../../tools/reference/README.md)
- **スクリプトは項目ごとに分ける**（1本にまとめない）。Phase 1 の制約カードは「信頼できた分析だけ載せる」方針なので、項目単位で差し替え・除外ができる粒度に保つ

### リファレンスの置き場は `<プロジェクト>/references/<リファレンス名>/`

共有ライブラリ（`~/Music/daw/references/` のような第2のルート）は**作らない**。LaLa は
`~/Music/daw/<プロジェクト>/` に全部入っている自己完結型なので、そこに揃える。

```
~/Music/daw/<プロジェクト>/
├── project.json
├── clip-NNN.wav
└── references/<リファレンス名>/
    ├── track.wav          分析対象（リージョンの範囲を書き出したもの）
    ├── stems/             htdemucs / htdemucs_6s
    ├── analysis/          分析の生データ(JSON)・図・MIDI
    ├── listen/            耳で検算する短いクリップ
    ├── card.json          制約カード（ガチャの入力。report.md と兄弟）
    └── report.md
```

- 共有ライブラリにしない理由: 命名規則・同じ曲を2プロジェクトで分析したときの重複・プロジェクト削除後に残る孤児、を全部考える必要が出る。横断レビューは `~/Music/daw/*/references/*/report.md` の glob で足りるので、第2のルートを作る理由になっていない
- プロジェクトを消すとレポートも消えるが、`report.md` は20KBなので必要なら手でコピーすればよい。それが痛くなるまでライブラリは作らない
- **保存時のクリーンアップとは干渉しない**: `Project::save` の未参照WAV削除は非再帰かつ `clip-*.wav` / `instr-*.wav` 限定なので、`references/` 配下は消えない
- **ただしリファレンス音源そのものは消える**: 取り込んだ音源は `clip-NNN.wav` なので、タイムラインからリージョンを外して保存すると実ファイルが削除される。**分析時にリージョンの範囲を `references/<名前>/track.wav` へ書き出す**こと（パイプラインはもともとトリム済みの `track.wav` を要求するので、トリムの入力元が変わるだけ）。取得したままの `source.wav` は保持しない
- **MVエディットのトリム判断が人手から消える**のがこの経路の利点。リージョンの範囲がそのままトリムになるので、波形とスペクトログラムを目視して ffmpeg で切る手順が要らなくなる

### 制約カード（card.json）— 分析とガチャのつなぎ（2026-08-04 確定）

分析結果のうち**ガチャの生成器が読む値だけ**を、パーツ別スライス（`global` / `drums` / `bass` /
`chords` / `arrangement`）に厳選した1枚。`references/<名前>/card.json` に置き、`report.md` と
兄弟になる（同じ分析の機械可読/人間可読）。スキーマの真実の源は
[`tools/reference/card.py`](../../tools/reference/card.py) と README（ここには方針だけ書く）。

- **制約は2分類**: (a) BPM・キーはプロジェクトへ**1回きりのコピー**で書き込む（リンクしない。
  リファレンスを差し替えても勝手に変わらない）。(b) それ以外（グルーヴ統計・密度・編成・構成）は
  プロジェクトの状態に昇格させず、**ガチャ実行時にカードを指すだけ**。二重管理を作らない
- **複数リファレンスはパーツ別参照**: ドラムは曲A・コードは曲B、のようにパーツごとに別カードを
  指せる（人間のプロデューサーの実際のリファレンスの使い方に近い）。**複数カードのブレンド（平均）は
  禁止** — 2曲のスウィング量を平均するとどちらの曲のノリでもない値になる（dB算術平均バグと同型）
- **生成は常にプロジェクトのキーで行う**。カードの `global.key` を生成時に読むことはない
  （プロジェクトキーと chords カードのキーが食い違ったとき生成先が不定になる）。
  「明暗」を借りたければその曲のキーをプロジェクトへコピーする、が唯一の経路
- **コード進行そのものは載せない**。chords スライスが運ぶのは性格
  （ループ長・変化の回数・ルートの方向・7th 系の有無）だけ。進行の実物は `analysis/` とレポートに残る
- **loop_bars は chords スライスにだけ置く**（出どころが harmony 分析なので、harmony 落ちで
  スライスごと消える）。パーツ別参照でカード間のループ長が食い違ったときの採用はガチャ側の決め
  （既定は chords カードの値）
- **ゲート落ちはスライス/フィールドごと省略**し、`meta.excluded` に `{path, gate, reason}` で残す。
  生成器は「無いなら自分のデフォルト」と解釈する。BPM/テンポのゲートが落ちた曲はカード自体を
  生成しない。harmony ゲートは**6分割の上モノだけ**で判定する（4分割 other は1本きりで合議できず、
  実際にループ長を誤答した。閾値も6分割の実測で較正されている）。source は usable かつ進行が
  抽出できたステムのうち**最大音量**（v1 の決め。複数ステムの進行が食い違うときの合議は
  入れておらず、必要になったら Phase 2 の生成器の要求で決める）

### ステム分離は4分割と6分割の両方を走らせる

`htdemucs`（4分割）と `htdemucs_6s`（6分割）は別々に訓練された別モデルで、共通のはずの
drums/bass/vocals も出力が違う。どちらかが優れているのではなく**用途で逆になる**ので両方使う。

- **ベース・ドラムは4分割**。ベースの調波打楽器比が 10.4 に対し6分割は 5.14 で、打楽器成分が倍入る
  （キック混入とみられる）。ピッチ追跡とオンセット位置が狂う
- **上モノは6分割**。piano/guitar/other の3本に分かれるので、同じコード検出を3回かけて検算できる。
  4分割は上モノが `other` 1本で検算できず、実際にループ長を 8小節 と誤答した
  （4小節=0.898 vs 8小節=0.913 の僅差。6分割の3ステムは揃って4小節）

**片方に絞ってもエラーは出ず、静かに劣化する**。時間とディスクが2倍かかるが、
分析の信頼度を落とさずに削る方法は今のところ無い。詳細は
[../../tools/reference/README.md](../../tools/reference/README.md) の「ステム分離とは / なぜ4分割と6分割を両方使うのか」。

### 深掘り対話の実装形態

レポートを読んで気になった箇所を AI に聞く経路。3案あり、**A から始めて、使うと分かったら C**。

- **A. ランチャー**（数十行）— 上の「このリファレンスについて聞く」。会話はターミナル。LaLa は AI 連携も
  APIキーも課金管理も持たない
- **B. フル自前** — Anthropic API を直接叩き、tool-use ループを C++ で実装する。**Claude Code のサブスクとは
  別に API 課金が発生する**ため不採用
- **C. アプリ内チャット＋Claude Code をバックエンド** — `claude -p --continue` を `SpawnedProcess` で叩き、
  結果を自前のペインに出す。APIキー・課金・ツール実行は Claude Code 側に乗るが、会話UIとプロセス配管は持つ。
  なお C は「表示UIは作らない」原則に対する**例外第2号**になる（第1号はレポート閲覧ウィンドウ。
  会話は開いたときだけとはいえ恒久的な画面要素）

**判断が変わる条件**: A を数回使ってターミナルへの移動が障壁になった / 音をその場で鳴らしながら会話したくなった。

### 分析の実行時間

4:35 の曲で通し **約2分**（analyze.py が依存グラフに沿ってステップを並列実行。旧直列版は約4分45秒だった）。
ボトルネックは demucs（GPU・計50秒）ではなく librosa 系 CPU ステップで、クリティカルパスは
basics → groove のベース pyin（Viterbi 追跡・約52秒。内部並列化不可＝これが下限）。
UXの流れの「進捗オーバーレイ」で待たせる設計として成立する。
