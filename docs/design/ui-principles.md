# UIデザインの判断軸

新しいUIを追加するとき・UIレビューに対応するときに、まずここに照らして表示の強さと置き場所を決める。

## 情報の強弱は視線頻度に合わせる

**プレイヘッド ＞ リージョン ＞ マーカー ＞ 小節番号**。

セクションマーカーは「地図」なので、薄い色帯＋開始線＋色文字で沈める（ベタ塗りにしない）。全体の方向性は Linear / Raycast 系の「ミニマルだが質感が高い」路線。アクセント色の運用ルールは `Source/ui/Theme.h` 冒頭のコメントに記載。

## 画面の性格で強弱方針を使い分ける

2026-07 のプロジェクト選択画面の刷新で確立。

- タイムライン等の**作業面は「沈める」**
- プロジェクト選択画面のような**ランチャーは華やかさ重視**（波形サムネイル・名前ハッシュから決まるプロジェクトカラー・ヒーローカード）

あわせて確定したこと:

- **UIの固定文言は英語を好む**（日本語ラベルは「ダサい」→ PROJECTS / Create / Today 表記に変更した）
- **同一情報の重複表示を嫌う**（ヒーローカードとリスト先頭行の重複は「リストは2番目以降＋ヒーローを選択と統合」で解消した）

## 操作導線の置き場所

2026-07 のバウンス導入で確立。

- **低頻度操作（書き出し等）はヘッダーの常設ボタンを増やさず、ネイティブメニューバー（File メニュー）に置く**
- 完了通知は「OKを押させるダイアログ」ではなく、オーバーレイの自動クローズ表示（約1.3秒）にする

**アプリのメタ情報（バージョン等）は作業面に出さない**（2026-07 のバージョン表示追加で確立）。置き場所は2つ:

- **ランチャーの見出し行の右端**（`PROJECTS` と同じ行に `v0.7.0`）— 起動のたび0クリックで目に入る。「更新が当たったか」の確認はここで済む
- **アプリメニューの About**（macOS標準パネル）— 調べに行く導線。`Check for Updates…` の直上に置いて更新まわりを1箇所にまとめる

タイムラインのヘッダーには置かない（常時見えるヘッダーにdB数値を置かないのと同じ理由＝作業中に読む必要がない情報）。2箇所に出るのは重複だが、性格が違う（勝手に目に入る／調べに行く）ので許容する。

## 開閉するUIは「開いたのと同じ操作」で閉じられる

2026-07 のデバイス設定の非モーダル化で確立。

- パネルも独立ウィンドウも、ボタンの再クリック／同じショートカットで閉じられるようにする（右パネル・FXパネル・ミキサーと同じ流儀）
- 閉じ方が ✕ だけのモーダルダイアログは避ける
- 開いている間はトグルボタンを ON 表示にして状態を見せる
- 例外: パネル自身に × がある常設系（左のFXパネル）は、ヘッダーのボタンを**閉じている間だけ出す戻り口**にする（2026-08-20）。常時出すとヘッダーのノイズになり、開いている間の「閉じる」は × と同じショートカットで足りる

## 日英混在時のフォントサイズ

「同じポイント数だと日本語が大きく見える」問題への方針（2026-07 確定）。2層に分ける:

- **固定UI文言はプラットフォーム標準サイズのまま補正しない** — Apple 自身が同ポイント方式で、縮めると OS 標準ダイアログと並んだときに日本語だけ小さく見える逆の違和感が出る
- **自由入力テキスト（トラック名・プロジェクト名等、日英の名前が並置される場所）だけ、CJK を含むときに約8%縮小**する — 混在文字列で欧文も一緒に縮む副作用は許容する（文字種ごとの分割描画は過剰）

判断の理由は「並置比較が起きる場所でだけ大小差が目につく」から。なお前提として、コントロール類がプラットフォーム標準サイズ（macOS なら13px）より大きいと日本語の大きさが露呈しやすい — **「日本語がでかい」と感じたら、まず標準サイズへの統一を先にやる**。実装は `Source/ui/Fonts.h` の `forText()`。

## 操作は削る、概念は隠さない

2026-08 のEQ設計で確立。「シンプルな操作感で無駄な情報を削りたい」と「音楽的な概念の学習を妨げたくない」の両立は、削る対象を**コントロール**に限定し、**実量と標準語彙**は隠さないことで実現する。

- **削るのはコントロール**: 使わない選択肢・モード・調整つまみは置かない（例: EQのバンドON/OFFはハイパスのみ・出力ゲイン非搭載・フィルタ傾き固定）
- **隠さないのは実量と標準語彙**: 数値は Hz / dB / Q の実単位で表示し、「明るさ」のような抽象ラベルに置き換えない。名称は一般的なDAW用語（ハイパス/ベル/シェルフ）を使う（LaLa独自語で完結させない、と同根）
- **操作を削って固定した値は、静的ラベルで見せてよい**（例: ハイパスに「12dB/oct」を添える）— コントロールを増やさずに概念だけ渡せる
- **実際の音の姿を見せる表示（アナライザ・メーター・波形）は「無駄な情報」に数えない** — 耳の感覚と数値を結びつける学習装置なので、装飾とは別枠で扱う

## 机と機材で文法を分ける（FX周りのルック）

2026-08 のFXパネル刷新で確立（plan: `docs/plans/2026-08-20-1836-fx-panel-hardware-look.md`）。

他のDAWと同じく、**アレンジ画面（トラック・リージョン・LCD・ミキサーのフェーダー）＝長時間見る地図は無彩色で沈め、FXパネル（左ラック・下部詳細・ノブ）＝いま触っている楽器は別の温度で描いてよい**。LaLaは host と plugin を両方自作しているので無意識に一つのトーンで揃えていたが、分けることで「トラック周りは決まり・FXは及第点」の差を埋めた。境界は FX パネルの上端1pxの縁。

- FX周りは **Illustrated hardware**（Soundtoys 系の温度。地に微かな質感・金属風ノブ＋点灯目盛り・グラフは内側に沈めた「メーター窓」・ラベルは大文字トラッキング）。**配置は LaLa のまま**で、実機の配置（Massive X 等）は真似しない（かっこいいが使いにくい）。描画は `Source/ui/HardwarePanelStyle.h` に集約し、各 View は呼ぶだけ
- **1FX 1色**: エフェクトごとに固有色（`Theme::fxHue (FxVisualKind)`）。使ってよい場所は **①処理を表す線（伝達カーブ・GR・倍音・EQカーブ）②ノブの点灯目盛り ③ラックLEDと選択枠** の3箇所だけ。地・ノブ本体・ラベル・数値・タイトルには使わない。面積を絞るから10色に増えても地の質感が勝つ。**数値の意味を色で伝えるメーター（LUFSの緑黄赤・相関の正負・クリップ赤）は既存の意味色を維持**する
- 新しいFXを足すときは `FxVisualKind` に1つ増やし、`Theme.h` の予備色（rose / yellow / ice）から割り当てる
- ラックのピルは ON/OFF を「青塗り／グレー」でなく **LED の点灯／消灯** で示す。パネルを開く前に「どのFXが効いているか」を色で読める。Instrument・Ext（`neutral`）にはLEDを描かない

## 意図的な見送りリスト

2026-07 のUIレビュー対応時に判断。**再提案されても原則不採用**（理由を添えて断る）。

- **トラックヘッダーへの情報追加**（Input / Stereo / 録音アーム R 等）— 引き算コンセプトに反する。モノ録音固定・選択トラック録音方式なので、表示する情報自体が無い
- **ボタンの内側シャドウ・1pxハイライト** — ミニマル方針と矛盾。hover 明化＋押下沈み込みの2状態で足りる（**トラック画面側の話**。FXパネルは「机と機材で文法を分ける」節のとおり質感を持たせる）
- **押下のスケールアニメーション** — トランスポートは即時反応が最優先。録音グロー明滅は実装済みで十分
- **マーカー文字の太字化** — SF Mono の合成ボールドは滲むリスクがある。色文字化で可読性は足りている
- **ルーラーとマーカーレーンの入力統合** — シークとマーカー編集のクリックが衝突する。統合は見た目だけ（背景同色・小節線の延長）に留め、ヒットテストは上下分離を維持する
- **複数プロジェクトの同時オープン（アプリ内マルチウィンドウ）** — 詳細は [feature-scope.md](feature-scope.md)

**なぜリスト化するか**: UIレビューを受けるたびに同種の装飾追加が再提案されるので、見送り理由を忘れると再検討の無駄が生じる。
