# オーディオリージョンのフェードイン/フェードアウト

## 概要・やりたいこと

オーディオリージョン（`Clip`）に非破壊のフェードイン/フェードアウトを持たせ、**リージョン上辺の左右のドラッグハンドル**で長さを決められるようにする。

### なぜ必要か

- **段差（クリック）を消す唯一の手段になる。** リージョンの端が「波形の途中の値」のまま無音に接すると、コーンが1サンプル（48kHzで0.021ms）で叩き落とされ、全周波数にエネルギーを持つ「プチッ」が鳴る。これは⌘Tで分割して**片方を移動・削除・ミュートしたとき**に必ず起きるが、現状これを直す手段がゼロ
- **語尾・息継ぎの処理。** リージョンゲインは「区間全体を一律に下げる」ことしかできず、「だんだん消す」ができない。ボーカルの語尾の伸ばしやノイズの立ち上がりは時間方向の傾斜を要求する
- **取り込み素材の頭/尻の整形。** 購入ビートやリファレンス音源を⌘Tで切り出して使うとき、切り口が必ず段差になる

`docs/design/region-settings.md` の項目表に「フェードイン/アウト｜リージョン上角のドラッグハンドル（ホバー/選択時に表示）｜波形上にカーブを描画。数値表示なし」として既に載っており、**未決だった「ヒット領域設計」を今回決めた**（10px × 14px）。

### 段差と角（dig中に実測して整理した）

検証ページ: `scratchpad/click-and-fade-demo.html`（合成音＋波形の拡大表示＋数値の裏取り）

| 現象 | いつ起きるか | 聴こえ方 | 直し方 |
|---|---|---|---|
| **段差**（値の不連続） | リージョン端が波形の途中の値のまま無音に接したとき | はっきり「プチッ」。素材を問わない | フェードを入れる（リニアで十分。数msで消える） |
| **角**（傾きの不連続） | リニアのフェードの開始点・終了点。短いほど強い | ごく僅かな「コツ」。5ms以下＋低音のときだけ | 手で引くフェード長（20ms以上）では**対処不要** |

- 段差は `-6dB/oct`、角は `-12dB/oct` で減衰する＝**桁違いに弱い**。手で引くフェードでリニアを選ぶ判断に影響しない
- **⌘Tで分割しただけでは、どちらも起きない**（左右が隙間なく連続再生されて元の波形を再現する）。片方を動かした瞬間に、露出した端が段差になる
- 端の値がゼロ交差なら、フェード無しでも段差は生まれない（デモの「切る位置: ゼロ交差」で実演）

### オートメーションを見送った理由（曲末フェードの動機で作りかけたので記録する）

オートメーションを入れると、音量の出どころが「フェーダー（手）」と「カーブ（再生ヘッド）」の**2つ**になり、どちらが勝つかを人間が管理する必要が出る。どちらに決めても間違う場面があるため、全DAWが **Read / Touch / Latch / Write / Off** という**モード**をユーザーに選ばせている（Logicは `A` でオートメーション表示をONにするとトラックヘッダーに出る）。

具体的な壊れ方 — マスターに曲末フェードを1本引いた翌日、曲全体を1dB上げたくてフェーダーを掴むと:

- **Read**: フェーダーが手から逃げて戻る（動かしても音が変わらない）
- **Off**: フェーダーは動くが曲末フェードが鳴らなくなる
- **Touch**: 離した瞬間に戻る＋触った区間のカーブが上書きされる
- **Latch / Write**: 停止するまで書き込み続け、通過したカーブを消していく

そして正解はこの5つのどれでもなく「カーブ全体の平行移動」なので、DAWはさらに **Trim / Relative**（カーブへのオフセット層）を足す。**1本のフェーダーの裏に3つの数字**がいる状態になる。

このコストは **恒常的ではなく休眠型**である点が重要。カーブを1本も引いていなければ Read は素のフェーダーと同じに振る舞うので、普段は何も見えない。だが一度引くと「フェーダーが効かない」が予告なく起き、原因の診断には5モード＋Trimというモデル全体の理解が要る。使用頻度が「1曲に1回」であることを考えると、**不意打ちの深さに対して見返りが小さい**。

波及して壊れるものも大きい:

- **データの流れが双方向になる**。現在は UI → モデル → エンジンの一方通行だが、フェーダーがカーブに追従するには エンジン → UI の逆流（30Hzで現在値を吸い上げ）が要る
- **undoの粒度**。Latchで10秒フェーダーを触ると数百点が書かれる。今回「ドラッグ1回＝1件」で揃えた約束がここだけ別ルールになる
- **リージョンゲインと役割がかぶる**。リージョンゲインは「オートメーションを持たない方針の穴埋め」として作った機能（`docs/plans/2026-07-26-region-gain.md`）なので、「曲の途中で音量を変える」手段が2通りになる
- **行の高さが可変になる**。オートメーションレーンを出すと `trackHeight` 固定の前提が崩れ、`row = e.y / trackHeight` 型の計算が33か所ある（`Source/ui/*.cpp`, `*.h`）

一方「曲末フェード＝数値1つ」案がモードを必要としないのは、それが**フェーダーとは別の場所にある独立した値**だから。Masterフェーダーは今までどおり手で決める設定のままで、その後段にランプが1本掛かるだけなので取り合いが起きない。同じ結果が出て覚えることはゼロ。**オートメーションの本質的なコストは機能の量ではなく「見えない状態が行動の意味を変える」ことにある。**

### 実装方針（調査済み）

#### モデル

```cpp
// Clip に追加（サンプル単位・絶対時間。BPM変更の影響を受けない）
juce::int64 fadeInSamples = 0;
juce::int64 fadeOutSamples = 0;
// 不変条件: 0 <= fadeInSamples, 0 <= fadeOutSamples, fadeInSamples + fadeOutSamples <= totalLengthSamples()
```

**クランプ規則と、それを通す経路**（`MidiRegion::clampNote` と同じく**モデル層で不変条件を強制**する）

```cpp
void Clip::clampFades()   // 規則: fadeIn を先に頭打ち → 残りで fadeOut を頭打ち
{
    const auto total = totalLengthSamples();
    fadeInSamples  = juce::jlimit ((juce::int64) 0, total, fadeInSamples);
    fadeOutSamples = juce::jlimit ((juce::int64) 0, total - fadeInSamples, fadeOutSamples);
}
```

- 「比率維持」にしない理由: フェード長はユーザーが**絶対時間（ms）で決めた値**なので、全長が変わるたびに勝手に伸縮すると意図が壊れる。単純な頭打ちなら決定的で、読込・分割・ループ変更のすべてで同じ関数を通せる
- 通す経路: **読込 / `splitClip` / フェードのドラッグ / ループ解除（`clearLoopAt`）/ ループのドラッグ**
- **⚠️ フェードのドラッグだけは `clampFades()` を直接通してはいけない。** この関数は fadeIn 優先なので、`fadeIn` を伸ばすと `fadeOut` が押し縮められる（全長100・fadeOut=40 のとき fadeIn を80にすると fadeOut が20へ削られる）。これは「相手を押しのけない」というドラッグの規則に反する。**ドラッグ側で先に相手の手前へ制限してから** `clampFades()` を通す（通した時点では no-op になる）:

```cpp
// fadeIn のドラッグ
clip.fadeInSamples  = juce::jlimit ((juce::int64) 0, total - clip.fadeOutSamples, dragged);
// fadeOut のドラッグ
clip.fadeOutSamples = juce::jlimit ((juce::int64) 0, total - clip.fadeInSamples,  dragged);
clip.clampFades(); // 保険（全長が別要因で変わっていた場合のみ効く）
```

- fadeIn 優先の非対称性が意味を持つのは**ループ縮小のときだけ**（そこでは「どちらかを削るしかない」ので決定的な規則が要る）
- **ループのドラッグは毎イベントで `clampFades()` を通すが、クランプ元は「ドラッグ開始時に控えた値」にする。** `handleLaneMouseDrag` は `clip.loopCount = snappedLoopCount;` を毎イベント代入して即repaintしている（`TimelineView.cpp:1407`）ため、確定時にだけクランプするとドラッグ中ずっと不変条件が破れる。かといって現在値からクランプすると、**縮めすぎてから戻してもフェードが復元されない**（1ジェスチャー内で値が削られる）。`RegionDrag` に `origFadeInSamples` / `origFadeOutSamples` を持ち、毎イベント「元値を代入 → `clampFades()`」で再計算する（`origStartSample` / `origLoopCount` と同じ既存パターン）

#### `ClipPlayback` は**絶対位置**でフェードの境目を持つ

ループ展開（`appendClipPlaybacks` = `Project.cpp:110`）は反復ごとに `ClipPlayback` を分けるため、「連なり全体の両端」のフェードは**複数の `ClipPlayback` をまたぐ**（例: 1小節×4ループに2小節のフェードアウト）。相対長で持つとまたぎを表現できないので、絶対サンプル位置で4つの境目を持たせる。

```cpp
// ClipPlayback に追加（すべて絶対サンプル位置。全反復に同じ値が入る）
juce::int64 fadeInStart = 0,  fadeInEnd = 0;   // fadeInEnd  <= fadeInStart なら フェードイン なし
juce::int64 fadeOutStart = 0, fadeOutEnd = 0;  // fadeOutEnd <= fadeOutStart なら フェードアウト なし
```

#### 音を出す箇所は3つ。区間分割は共有ヘルパーに集める

`PlaybackEngine` モノ経路（`:281`）・ステレオ経路（`:355`）・`BounceRenderer`（`:277`）はいずれも `addFrom (..., 定数gain)` で、**定数ゲインではフェードを表現できない**。重なり範囲を最大3区間（フェードイン部・平坦部・フェードアウト部）に割り、平坦部は `addFrom`、傾斜部は `addFromWithRamp` を使う。

```cpp
// shared/ClipFade.h（新設）
namespace ClipFade
{
    struct Segment { int destOffset; int count; float startGain; float endGain; };
    // [overlapStart, overlapEnd) を最大3区間へ。フェードが無ければ 1区間・startGain == endGain == 1.0f
    int segments (const ClipPlayback& clip, juce::int64 overlapStart, juce::int64 overlapEnd,
                  juce::int64 segPos, Segment* out); // 戻り値 = 区間数 1..3
}
```

**エンベロープの定義（閉区間・両端が厳密）**

フェードは**両端を含む閉区間**として定義する。`n` サンプルのフェードインなら先頭サンプルのゲインが厳密に `0`、`n` 番目（index `n-1`）が厳密に `1`。フェードアウトも同様に**最終サンプルのゲインが厳密に `0`**。

```
fadeIn  (n = fadeInEnd - fadeInStart):    g(s) = (s - fadeInStart) / (n - 1)
fadeOut (n = fadeOutEnd - fadeOutStart):  g(s) = (fadeOutEnd - 1 - s) / (n - 1)
n <= 1 のときは g = 0（1サンプルのフェード＝そのサンプルが無音）
```

半開区間（`n` で割る）にすると最終サンプルにゲイン `1/n` が数学的に残り、**段差が消え切らない**（`n=240` で -47.6dB、`n=1` では素通しで無意味）。段差を消すことがこの機能の第一目的なので閉区間を採る。`scratchpad/click-and-fade-demo.html` の実測（5msフェードの最後の4サンプル = `0.0076, 0.0050, 0.0025, 0.0000`）もこの定義。

- **JUCEの `addFromWithRamp` はこの定義をそのまま再現できる。** `endGain` は「**最終サンプルの次に適用される値**」で、サンプル `i` のゲインは `startGain + i / numSamples * (endGain - startGain)`（`build/_deps/juce-src/modules/juce_audio_basics/buffers/juce_AudioSampleBuffer.h:877` のdocに明記）。つまり **`endGain` に「区間の排他端で評価したエンベロープ値」を渡せば**、上の定義どおりのランプになる
- **`endGain` は実際には適用されないので、`[0,1]` を外れてよい**（フェードアウト区間の排他端では負、フェードイン区間の排他端では `n/(n-1) > 1` になる）。ここでクランプすると傾きが狂うので **クランプしないこと**

**⚠️ 最終ゲインは「厳密に0」にはならない（float の累積誤差）**

`addFromWithRamp` の実装は `startGain += increment` をサンプルごとに繰り返す（同ヘッダ `:898`）ため、数学上の値からずれる。ただし**この設計はブロックごとに絶対位置から `startGain` / `endGain` を評価し直すので、誤差はフェード長ではなくブロック長で頭打ちになる**。実測（float32・閉区間定義でのフェードアウト最終サンプルのゲイン）:

| フェード長 | 一括処理 | block=512（実際の経路） | 半開区間なら（数学値 `1/n`） |
|---|---|---|---|
| 240サンプル（5ms） | -2.797e-6（-111.1 dB） | 同左（1ブロックに収まる） | 4.167e-3（**-47.6 dB**） |
| 96000サンプル（2s） | -9.900e-4（-60.1 dB） | -1.778e-8（-155.0 dB） | 1.042e-5（-99.6 dB） |
| 384000サンプル（8s） | -2.667e-3（-51.5 dB） | -1.646e-9（-175.7 dB） | 2.604e-6（-111.7 dB） |

- 計測した範囲（240 / 96000 / 384000サンプル × block=512）では**残差の最大は 2.8e-6（-111dB）で、240サンプルのケースが最悪**。可聴域から遠いので、端点を別扱いにして加算をスキップする特別扱いは**入れない**（3か所の合成ループを複雑にする見返りがない）
- したがってテストは**厳密な0ではなく許容誤差 `1e-4`（-80dB）で判定する**。判定には**240サンプルのフェードを使う**こと。この条件なら float誤差（実測 2.8e-6）より閾値が十分大きく、半開区間へ退行したときの残差（4.2e-3）より十分小さいので**回帰を検出できる**。長いフェードで判定してはいけない（半開区間でも `1/n` が小さく通ってしまう）

**⚠️ ブロックサイズが変わると出力はビット一致しない**

区間の切れ目が変わると float の累積のしかたが変わるため、同じフェードでもブロックサイズ次第で結果がずれる。実測（block=1024 基準の最大サンプル差）:

| フェード長 | B=64 | B=128 | B=256 | B=512 |
|---|---|---|---|---|
| 240 | 3.13e-6 | 3.13e-6 | 0 | 0 |
| 960 | 1.40e-5 | 1.40e-5 | 1.40e-5 | 1.40e-5 |
| 2400 | **2.41e-5** | 2.25e-5 | 1.93e-5 | 1.28e-5 |
| 96000 | 1.35e-5 | 1.26e-5 | 1.08e-5 | 7.21e-6 |

- **バウンスは 1024 固定**（`BounceRenderer::renderBlockSize`・`BounceRenderer.h:30`）、リアルタイムはデバイス依存。つまり**再生とバウンスは原理的にビット一致しない**
- 既存の `testEngineBounceStereoConsistency` は engine=512 / bounce=1024 で **`maxDiff < 1.0e-4f`** 判定になっており、実測の最悪 2.41e-5 に対して4倍の余裕がある。**フェードを足しても閾値の変更は不要**
**区間の継ぎ目で連続なのは「適用されるゲイン」であって「パラメータ」ではない**

- **同じ傾斜の途中でブロック分割したとき**は、前区間の `endGain` と次区間の `startGain` が同じ絶対位置の評価値になるので**パラメータが一致する**
- **傾斜 ↔ 平坦 ↔ 無音の境界では一致しない。** フェードイン終端の排他端の外挿値は `n/(n-1)`（>1）だが、次の平坦部の `startGain` は `1`。フェードアウト終端の外挿値は負だが、その先は無音。**実際に適用される値**（前区間の最終サンプルと次区間の先頭サンプル）は連続するので正しい
- したがって**パラメータの一致を検証してよいのは同一傾斜内の分割だけ**で、区間種別をまたぐ境界は**実適用ゲインで検証する**

- **ビット一致を守る**: フェードが無ければ「1区間・ゲイン1.0f」に落ち、呼び出し側は `addFrom (ch, destOffset, src, count, clipGain * 1.0f)` を1回だけ呼ぶ。`x * 1.0f` はIEEE754上 `x` と厳密同値なので、既存プロジェクトの出力ハッシュは変わらない**はず** → `testMonoRenderRegressionHash` で必ず裏を取る

#### ドラッグ中の音への反映

リージョンゲインで作った経路をそのまま使う。フェード長の変更はノート・リージョン・トラック構成・音源を一切変えないので `audioValuesOnly` の条件を満たす。

- `Project::SnapshotChange::audioValuesOnly` → `MainComponent::pushAudioValueSnapshot()`
- `UndoStack::EditKind::clipValue`（`UndoStack.h:28`）→ `MainComponent::afterHistoryRestore` の既存の枝がそのまま効く
- コールバック `onWillEditClipGain` / `onClipGainEdited`（`TimelineView.h:73-74`）は**「クリップのオーディオ値」共通の経路**になるので `onWillEditClipValue` / `onClipValueEdited` へリネームする（`MainComponent.cpp` の配線も同時に）

#### 描画とヒットテストの基準は「本体」ではなく「連なり全体」

`drawClip` の `rect`（`TimelineView.cpp:614`）は**1反復分の本体だけ**で、ループ終端は別変数の `loopRight`（`:610`）。フェードは連なり全体の両端に掛かるので、**本体rectでクリップすると2反復目以降のフェードアウトが音には掛かるのに画面に出ない**。

```cpp
const auto bodyRect  = juce::Rectangle<int> (x, y + 4, w, trackHeight - 8);              // 既存。波形・名前・バッジ用
const auto chainRect = juce::Rectangle<int> (x, y + 4, loopRight - x, trackHeight - 8);  // 新設。フェードの描画・ハンドル用
```

- 斜線・暗がり・ハンドル位置・ハンドルのヒット領域・「幅40px未満なら出さない」判定は**すべて `chainRect` 基準**
- 波形・表示名・ゲインバッジは従来どおり `bodyRect` 基準（変えない）
- `chainRect` は `drawLoopBand` が敷く帯（`:562`）と同じ矩形なので、角丸4pxでのクリップもそのまま使える

#### フェードイン/アウトのハンドルが重なったとき

`fadeIn + fadeOut == 連なり全長` を許すので、2つのハンドル（各10px幅）は**近づくと重なり、上限では完全に一致する**。固定順で判定すると片方が掴めなくなる。

- **規則: クリック位置に近い方を選ぶ。等距離ならフェードイン優先**
- 詰まないことの保証: フェードインを縮めればフェードアウトのハンドルが必ず露出するので、片方が永久に触れなくなる状態にはならない
- 「左半分/右半分で役割を分ける」案は却下（フェードインが中央を越えた瞬間にフェードインのハンドルが右半分へ入り、逆に掴めなくなる）

#### 描画で衝突するもの

| 相手 | 位置 | 対処 |
|---|---|---|
| ゲインバッジ | 本体右上 `right-34 .. right-4`（`TimelineView.cpp:595`） | フェードアウトハンドル（fadeOut=0 のとき `right-10 .. right`）と6px重なる → **バッジの右マージンを 4px → 14px** にして常時10px左へ寄せる（選択状態で動くとちらつくので条件分岐にしない） |
| 表示名 | 本体左上 `x+6`（`TimelineView.cpp:677`） | **重なりは許容**。ハンドルはフェード終端に追従して動くので、名前の途中に重なるケースは余白調整では原理的に消せない。Logicも同じ状態で、ハンドルは選択中のみ・名前は副次情報 |
| ループハンドル | 本体**下辺**の右寄り（`loopHandleRect`） | 辺が違う（上辺 vs 下辺）ので衝突しない |
| 移動ドラッグ | 本体全域 | 判定順を「フェードハンドル → ループハンドル → 移動」にする。加えて**連なり全体の幅が40px未満ならハンドルを出さない**（10pxハンドル2つ＋移動用の余白20pxを確保。バッジの56px閾値と同じ考え方） |

### 注意点

- **`PlaybackEngine.cpp:250` の「このブロックは演算順序を含め一切変えないこと」**（ビット一致の回帰コメント）。区間分割を挟むので、フェードなしのときに完全に既存の形へ落ちる構造にすること
- **再生と書き出しは2経路**（`PlaybackEngine` と `BounceRenderer` が別実装）。片方だけ直すと「聴こえ方と書き出しが違う」になる
- **ループ回数を変えるとフェードの再クランプが要る**。下辺ハンドルのループ縮小・右クリックの「ループ解除」（`clearLoopAt`）で連なり全長が縮み、`fadeIn + fadeOut > 全長` になりうる。**ループドラッグは毎イベント代入なので、確定時にだけクランプすると不変条件が破れる**（上記「クランプ規則と、それを通す経路」の元値方式で解く）
- **`splitClip`（`Project.cpp:72`）は `left = clip` で丸ごとコピーしている**。フェードを足すと左が元のフェードアウトを、右が元のフェードインを引き継いでしまい、分割点にフェードが移動する。明示的に内側を0にする
- 変更前の回帰ハッシュ（`45008a7` 時点・実測済み）: `hash-engine: 59c79a3b0352743f` / `hash-bounce: 96f5e41dc31e0732`
- **テストで `SnapshotExchange` に3回以上pushするときは間に `deleteRetired()` が必要**（`acquire()` は retired が空のときだけ pending を取り込む。リージョンゲイン実装時に一度誤診した）

### 試したこと・わかったこと

- dig中に作った検証物:
  - `scratchpad/region-fade-mock.html` … 見え方3案の比較＋ハンドルのヒット領域を実マウスで試す＋カーブ4種の視覚/聴覚比較。これで「10×14px」「案B」「リニア」を決めた

- **モックのエンベロープに上下逆のバグがあり、一度誤った比較をさせた**。末尾から数えて `i=0`（最後のサンプル）にゲイン1を入れており、フェードを掛けたはずの波形が「最後だけフル音量」のままだった。4案すべてが同じ段差0.60で鳴っていた。修正後に数値で裏を取った（フェード5ms → 最後の4サンプルが `0.0076, 0.0050, 0.0025, 0.0000`）。**モックでも出力の数値検証をしてから見せること**
- 既定ズーム（120bpm・80px/小節）は **25.0 ms/px**。320px/小節で6.3ms/px、上限640px/小節で3.1ms/px。5ms級のフェードは上限ズームでも3pxで手では引けないが、20〜50msなら6〜16pxで引ける — これが「クリック除去の自動化を入れない」判断の根拠
- 他DAW調査: 曲末フェードは Logic / Pro Tools / Live / Reaper すべて**マスターのボリュームオートメーション**が標準手段で、リージョンフェードでやるDAWは無い。精密値の逃がし先は**数値入力欄**（Logicのリージョンインスペクタ・Reaperのアイテムプロパティ）で、fine-drag修飾キーは一般的でない
- **`addFromWithRamp` の float 累積誤差を実測した**（`startGain += increment` をサンプルごとに繰り返す実装。`juce_AudioSampleBuffer.h:898`）。planレビューで「厳密に0にはならない」と指摘されたのを受けての計測:
  - **ブロックごとに絶対位置から `startGain`/`endGain` を評価し直す設計なら、誤差はフェード長ではなくブロック長で頭打ちになる。** 2秒のフェードでも一括処理なら -60dB 残るが、block=512 なら -155dB
  - 最終サンプルの残差の最悪は**240サンプル（1ブロックに収まる短いフェード）の 2.8e-6（-111dB）**。長いフェードほど小さい
  - **ブロックサイズ違いの出力差は最大 2.41e-5**（N=2400・B=64 vs B=1024）。1e-5 では足りず、汎用に比較するなら 1e-4 が要る
  - この手の「許容誤差いくつ？」は推測せず、**JUCEと同じ float 加算を再現して測ってから決める**のが速い（node の `Math.fround` で足りる）
- **ドラッグの検証は合成MouseEventをレーンへ直接送る形で自走できた**（実機・CGEvent不要）。`Viewport::getViewedComponent()` でレーンを取り出し、`juce::MouseEvent` を組んで `mouseDown` → `mouseDrag` を送る。1ジェスチャー内で複数の drag を送れるので「ループを縮めてから同じジェスチャー内で戻す」経路依存の検証まで通った（手順は VERIFY.md に記録）。実測値:
  - フェードイン上限まで引く: `fadeIn=288000` / `fadeOut=96000`（全長384000）＝相手を押しのけていない
  - ループ縮小→復元: `loopCount 3→0` で `fadeIn=96000 / fadeOut=0` まで削られ、戻すと `96000 / 192000` に**復元**（元値方式の証明）
- 描画の確認は「ケースごとに描いて該当行だけ切り出し、1枚へ縦に積む」方式にした（選択は1つしか持てないので、選択中のみ出るハンドルを複数ケース並べるにはこれが要る）

### 方針変更

- **`ClipFade::Segment` に `ramp` フラグを足した**（当初案は `startGain == endGain` で平坦/傾斜を判定）。理由は2つ: ①`-Wfloat-equal`（`juce_recommended_warning_flags`）で警告が出る ②平坦部を「必ず `addFrom`」へ落としたいので、区間種別で決める方が意図に忠実（ゲインの値がたまたま一致したかどうかで経路が変わらない）
- **フェードドラッグのクランプを TimelineView 直書きから `Clip::clampedFadeIn/clampedFadeOut`（モデル層の純関数）へ移した。** planの式（`jlimit(0, total - 相手, dragged)`）そのままだが、モデル層に置いたことで「相手を押しのけない」規則を `daw_tests` から直接検証できる（UI層のドラッグ処理をテストへリンクせずに済む）
- **ハンドルの矩形計算と掴み分けを `TimelineView` の static inline ヘルパー（`fadeHandleRectAt` / `pickFadeHandle`）に切り出した。** ヘッダだけで完結するので、`daw_tests` に `TimelineView.cpp` をリンクせずに「重なり時の選択規則」「連なり内へのクランプ」をテストできる
- **「再生中に audioValuesOnly をpushしてもMIDIの発音が途切れないこと」は専用テストを作らず、既存 `testAudioValuesOnlySnapshot` にフェードのケースを1つ足した。** 経路（`SnapshotChange::audioValuesOnly`）はリージョンゲインと完全に同一で、MIDI側の非破壊性は同テストの後半が既に検証しているため（重複テストを増やさない）
- **ゲインバッジとフェードアウトハンドルの重なりは「休止位置だけ」解消した。** 右マージン4px→14pxで `fadeOut=0` のときの6px重なりは消えるが、フェードアウトが9〜39pxのときはハンドルがバッジの上に来る（ハンドルはフェード終端に追従するので余白では原理的に消せない — planが表示名について書いたのと同じ理由）。バッジを後に描くのでdB値は読める

### 想定外の失敗

- **ループ済みクリップの分割で不変条件が破れていた**（レビュー指摘。`splitClip` は `loopCount` をコピーしたまま `clampFades()` を通し、その後 `splitAtPlayhead` がループを解除していたため、フェードが分割後の全長を超えて残る）。**描画は未クランプ値・再生は `appendClipPlaybacks` の防御クランプ値**を使うので「見た目と音が食い違う」＋保存→再読込で値が変わる。修正は **`splitClip` 側でループ解除をクランプより先に行う**（呼び出し側の解除は削除。返ってきた左右が常に不変条件を満たす形にした）。**旧順序に戻すとテストが落ちることを実測で確認**（`左右のフェードが分割後の全長に収まること` 他2件がFAIL）
  - 教訓: 「モデル層で不変条件を強制する」と決めても、**呼び出し側が後からクランプの前提（全長）を変えると破れる**。全長を決める値（`loopCount`）の変更は、必ず同じ関数の中でクランプより先に済ませる
- **エンジン出力の「素の振幅」を厳密一致（`exactlyEqual`）で判定して落ちた。** panセンターのモノゲインは `cos(π/4) * √2` で、floatでは 1.0 にわずかに満たない（既存 `testEngineClipGain` が許容誤差 0.001 を使っているのはこのため）。フェード外の平坦部は `1e-6` の許容誤差で判定するように直した
