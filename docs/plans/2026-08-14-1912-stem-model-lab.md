# ステム分離モデル選定ラボ — demucs vs BS-RoFormer SW

## 概要・やりたいこと

Salvaのステム分離で使うモデルを、「自分で作れる最高品質」の基準で選定する。既存資産（demucs）を理由に確定させず、現時点の最上位候補と実素材・実マシンで比較して決める。

**SalvaとreferenceパイプラインはKPIが別なので、採用判定も別に行う**:

- **Salva採用モデル**（このplanの主目的）: 「耳で使える分離音」が基準。ブラインド試聴で決める
- **reference-beat採用モデル**（副次判定）: 「下流分析が正しくなるステム」が基準。既存設計はベース・ドラム=4分割/上モノ=6分割を意図的に使い分けており（reference-beat.md「ステム分離は4分割と6分割の両方を走らせる」）、耳の勝敗では更新しない。グルーヴ位置・ベース音高・コード骨格/ループ長・ゲート通過状況を**人間確認済みの正解と照合**して初めて序列を動かす（BPM等、元音源だけから算出される項目は対象外 — 詳細はPhase 3.5）
- 結論が「SalvaはSW、分析は現行demucs併用」に割れてよい。reference側の回帰比較は本ラボの出力を流用した別判定とし、材料が揃わなければ「未判定のまま現行維持」で終えてよい

- Salva側は `separate.sh` の契約でモデル非依存にしてあるため、ラボの結論は主にスクリプト差し替えで反映できる（Salva実装をブロックしない。着手はSalva先行と決定済み）。ただし**venvとキャッシュの2点は差し替えだけでは済まない**（Phase 4に明記）
- 結果は `docs/labs/reference-beat.md`（追記専用）へ記録する。`docs/design/reference-beat.md` のモデル序列は**reference側の回帰比較が済んだ範囲だけ**更新する

## 判定基準（試聴前に固定）

**比較・採点の単位は「候補モデル」ではなく「Salvaのステムグループ」**（4 STEMS枠 / 6 STEMS枠）。候補ごとに出力グループ数が違う（現行demucsと多段=2グループ、SW単発=6ステム1グループ）ため、モデル単位で比べると4ステム枠にpiano/guitarが無く主評価軸を採点できず、SWだけ1出力で不利になる。

- **4 STEMS枠の候補**: 現行 `htdemucs` vs 多段の4ステム側。主評価軸は vocals⇄other 間の漏れ
- **6 STEMS枠の候補**: 現行 `htdemucs_6s` vs SW単発 vs 多段の6ステム側。主評価軸は上モノ（piano/guitar）への滲み
- **部分採用を許す**（例: 「4ステムはdemucs維持・6ステムはSW」）。拒否条件・採用条件は以下をグループごとに適用する

試聴後に重みが動かないよう、役割を先に分ける:

- **速度・ピークメモリ = 許容上限**（採用条件ではない）: 1曲あたり実測5分以内・実行中に他作業が破綻しない範囲。上限内なら速いことは加点しない
- **耳の結果 = 採用条件**。採点尺度は事前固定: **-2 悪い / -1 少し悪い / 0 同等 / +1 少し良い / +2 良い**（現行demucs比）
  - **採点行の単位**: 曲×区間×対象ステム×軸。対象ステムは4枠=vocals/other、6枠=piano/guitar/other（再加算軸はステム無しで曲×区間×軸）
  - **拒否条件（1つでも該当したらそのグループでは不採用。他が全部良くても覆らない）**: 「本来の音の欠落」「金属的な揺れ・水中感」「アタックの崩れ」「再加算時の原曲との差」の4軸で、**個別行に -2 が1つでも付いた時点で発動**（曲内集約で薄めない — 明確な悪化がどこかで聴こえること自体が致命のため）
  - **曲内集約**: 主評価軸（グループ別定義）について、その曲の対象行（区間×ステム）の**中央値**をその曲のスコアとする
  - **採用条件**: 曲スコアが**曲単位の過半数（2曲なら2曲、3曲なら2曲）で +1 以上**、かつ全採点行の合計が非負
  - **N/A行の扱い**: activity判定（Phase 2）で採点不能とされた行は N/A とし、曲内集約の中央値・全行合計の**分母から除外**する
- 同点・条件未達なら現行demucs維持（移行コストを払う理由がない）

## 前提・わかっていること

- 既存: `tools/reference/` パイプラインで demucs（htdemucs＋htdemucs_6s）が本番稼働中。M系GPUで2モデル計約50秒/曲（reference-beat.md 記載）
- 調査済みの序列（reference-beat.md 2026-08-14）: 現行demucs ≒ 商用中位〜上位、最上位はBS-RoFormer系（重み公開・無料）で差はSDR 1〜2dB。品質はモデル差より**素材の薄さ**の方が効く
- Web裏取り（2026-08-14）:
  - **BS-RoFormer SW**: 6ステム（vocals/drums/bass/guitar/piano/other）、2026年2月時点で6分割の最上位と目される。重み約700MB公開。`bs-roformer-infer`（pip・初回自動DL）または `audio-separator` で実行可。ONNX版・GGUF版の配布もあり
  - 多段（RoFormerでボーカル/伴奏→demucsで伴奏をばらす）はコミュニティ（UVR/MVSEP）の標準手法
  - demucs単体6分割はボーカル滲みが4分割より多い、が通説
- 未知数: **Apple Siliconでの推論速度**（RoFormer系はdemucsより重い）・実素材での耳の差
- 耳確認など再取得できない人間判断は `docs/labs/reference-beat-human-answers/` にコピーを置く運用（既存ルール）

## 実装計画

### 事前準備 [人間👨‍💻]
- [ ] なし（素材は既存 `~/Music/daw/references/` のリファレンス曲を使う。レコードリップが間に合えば1曲追加すると素材の帯が広がる）

### Phase 1: 環境構築 [AI🤖]
- [ ] BS-RoFormer SW の実行環境を**既存venvとは別に**構築（`tools/reference/` の稼働中パイプラインを壊さないため。`bs-roformer-infer` か `audio-separator` を試し、動いた方を採用）
- [ ] 重みDL・1曲通しで動作確認（MPS/CPUどちらで動いているかも記録）
- [ ] 再現性の記録: パッケージ名とバージョン・checkpointファイル名と**SHA256**・推論設定（segment/overlap等の非デフォルト値）をログに残す（bs-roformer-infer自体が重み配布元消失への対応を謳っており、自動DL任せでは再現できなくなるため）。**多段候補で使うvocal特化モデルを含む全モデルに適用**する
- [ ] MLXネイティブ実装（`mlx-audio-separator`。同じ BS-Roformer-SW.ckpt を扱う）を比較対象に入れるか判断し、**入れない場合も除外理由を記録**（モデル品質と推論バックエンド速度を混同しないため。品質同一でApple Silicon速度だけ変わる位置づけなら「勝者確定後の高速化オプション」として後回しでよい）

### Phase 2: 比較実行 [AI🤖]
- [ ] **素材2〜3曲と試聴区間を実行前に固定**（編成の厚い曲・薄い曲を混ぜる）。各曲で以下3種の区間（各8〜16小節）を固定する — 主評価がボーカル漏れなので①を必ず含める:
  - ① ボーカルと上モノが重なる区間
  - ② ボーカルなしの薄い区間
  - ③ 編成が厚い区間
- [ ] 以下を**全候補・同条件で**実行:
  1. demucs htdemucs＋6s（現行ベースライン）
  2. BS-RoFormer SW 単発（6ステム）
  3. 多段（保険扱いにせず最初から同条件で回す。「期待外れなら後で実行」は条件が揃わなくなる）。構成は事前定義:
     - 2ステム化: vocal特化RoFormer（UVR/MVSEPで標準の最上位をPhase 1で選定し、名称・SHA256を記録）でvocals/instrumentalに分離
     - 楽器ばらし: instrumentalを現行と同じ `htdemucs`＋`htdemucs_6s` の2本に渡す
     - 最終ステム構成: vocals=RoFormer出力、それ以外=demucs出力（demucs側のvocals残渣は破棄）
- [ ] **各候補×各素材を最低2回実行**し、run間のステム差（RMS・ステム比）を記録する。現行demucsは同一入力でもステム比 -14.6〜-24.9dB の差が出ることが実測済み（labs 2026-08-03）で、単発比較だと「たまたま良かったrun」を選ぶ恐れがあるため。耳の判定に使うrunは機械的に決める（例: 各候補の1回目で統一）
- [ ] 速度・ピークメモリ・出力ステム構成・run間差を表にまとめる
- [ ] ブラインド試聴セットを準備（**2セットに分ける** — 正規化済みステムを足すとステム間の音量比が壊れ、再加算評価が成立しないため）:
  - 生の出力は無加工で保存（採点や後の分析はこちらを使う）
  - **セットA（ステム単体試聴用）**: 対応ステム間で同一ラウドネスへ正規化したコピー（音量差で判定が偏るのを防ぐ。ラウドネス差自体は表に記録）
  - **正規化の前にactivity判定を行う**（区間によってはpiano/guitarが鳴っておらず、漏れだけの微小ステムになる — labs実例: 上モノ無し曲のpianoが-68.8dB。これを通常音量へ持ち上げると、正しくほぼ無音にした候補ほど残留ノイズを大増幅して聴くことになり比較が逆転する）:
    - 両候補で対象音が有効 → ラウドネス一致して全軸を採点
    - 一方だけ有効 → 正規化せず共通ゲインで提示し、「欠落」軸で判定
    - 両方とも非アクティブ → 欠落・アタック軸は N/A
    - 非アクティブステムの漏れ比較 → 正規化せず、原曲に対する相対音量を維持して提示
    - activity判定の閾値と各行の判定結果・根拠は対応表ファイルへ一緒に保存する（後から再計算できるように）
  - **セットB（再加算試聴用）**: 生ステムをそのまま加算し、**完成したミックス全体へ共通ゲイン1つだけ**を適用（原曲との比較用）
  - 提示は完全匿名の単独提示ではなく**「現行demucs 対 challenger」のペア（X/Y）単位**にする（全候補を匿名化すると、どれがdemucsか分からず「現行比 0=同等 / +1=少し良い」が付けられない）。ペアは 6ステム枠=「demucs_6s vs SW」「demucs_6s vs 多段6s」、4ステム枠=「htdemucs vs 多段4s」
  - 各ペアで**X/Yのどちらがdemucsかをランダム化**し、回答は「YはXよりどうか」を-2〜+2で採点。集計時に対応表を見て符号を変換し「demucs比」に直す
  - どちらも同一区間を切り出した匿名フォルダ構成にする
  - モデル名との対応表は**ファイルへ保存**する（`docs/labs/reference-beat-human-answers/<日付>-blind-map.json`。回答完了まで人間は開かない運用。AI側の記憶だけだとセッション消失で人間判断が再取得になる）。開示は**回答完了後**

### Phase 3: 耳確認 [人間👨‍💻]
- [ ] ブラインドで**ペア（X/Y）ごとに**聴き比べ、以下を**軸ごとに別々に**「YはXよりどうか」で採点（総合印象1個にしない）:
  1. 他楽器の漏れ（特に上モノへのボーカル/ドラム滲み）
  2. 本来の音の欠落
  3. 金属的な揺れ・水中感（アーティファクト）
  4. アタックの崩れ
  5. ステム再加算時の原曲との差
- [ ] 回答は `docs/labs/reference-beat-human-answers/` へ保存（対応表開示前の生回答のまま）

### Phase 3.5: reference-beat側の回帰比較 [AI🤖]（**耳結果とは独立に実行** — SWがSalva用途で負けても分析では勝ち得るため。Phase 2の生出力を流用する）
- [ ] **置換表を固定してscratchコピー上で実行**する。`analyze.py` は `stems/htdemucs/track/` と `stems/htdemucs_6s/track/` をハードコードしているため、そのまま実行するとdemucsを再生成するか既存demucsステムを読み、SWの改善として誤帰属する。分析器は改修しない:
  - **上モノ評価**: scratchコピーの `stems/htdemucs_6s/track/` 枠へSWの6ステムを配置、`stems/htdemucs/track/` は現行demucs出力のまま
  - **ベース・ドラム評価**: 別のscratchコピーで `stems/htdemucs/track/` 枠へSWの bass/drums/vocals を配置。**4分割枠の `other.wav` は SWの piano＋guitar＋other を生floatで加算して作る**（SWのotherだけを置くとpiano/guitarぶんの上モノが消え、topline・gateが「上モノ欠落」と誤判定する）。加算後にSR・長さを枠の契約どおりに揃えてから配置し、4分割枠の別条件として区別する
  - 結果の記録には**各指標が実際に読んだモデル**を必ず添える（枠名 ≠ 中身になるため）
- [ ] reference側の候補は**SW単発のみ**とし、「多段はSalva専用候補・reference側は未評価」とラボ記録に明記する（多段の楽器ばらしはdemucs自身なので、分析側の差分はボーカル抜き前処理の有無だけ。評価する価値が出たら別ラボ）
- [ ] 上記scratchでの判定は**人間確認済みの正解と照合できる項目に限定**する（既存demucs結果との差分だけでは「正解へ近づいた」と「別方向へずれた」を区別できない）:
  - 4分割枠: グルーヴ位置・ベース音高（`docs/labs/reference-beat-human-answers/` に正解がある曲・項目のみ）
  - 6分割枠: コード骨格・ループ長（同上）
  - gate: 正解が取れている項目を通過させ、誤答していた項目を落とせるか
  - 正解ラベルの無い数値は「変化量」として記録するだけで「改善」とは呼ばない
  - **BPM等、元の track.wav だけから算出される項目は比較対象から外す**（`basics.py` は track を直接読むため、ステム差し替えでは値が変わらず評価材料にならない）
- [ ] ただし**枠への配置だけで済まずアダプタ実装が必要になった場合は書かない**。その時点で「別ラボへ持ち越し・分析は現行demucs維持」と記録して打ち切る（本ラボのスコープは比較であって分析パイプライン改修ではない）
- [ ] 改善が確認できた項目だけ `docs/design/reference-beat.md` の序列・使い分けを更新。確認できなければ「分析は現行demucs併用のまま」で確定（Salvaの採用とは独立）

### Phase 4: 結論の反映 [AI🤖]
- [ ] 結果を `docs/labs/reference-beat.md` に追記（速度表・run間差・耳確認の結論・採用モデル・再現性情報）
- [ ] **venvの着地を決めて実施**（現状Salvaは `resolveVenvPython()` の既定 `~/daw/tools/reference/.venv` でスクリプトを実行するため、別venvのままでは差し替えだけで動かない）。どちらかに倒す:
  - reference venvへ依存を固定追加し、既存パイプライン（`analyze.sh` 一式）を全回帰確認する
  - Salva専用venvを正式化し、既定パス・アプリ内診断文・セットアップ手順（`mise run ref:setup` 相当）を更新する
- [ ] **各枠の勝者から最終パイプラインを構成**して `separate.sh` に固定する。部分採用の場合は複合構成になる（例: 「4ステム=htdemucs・6ステム=SW」なら1スクリプトが両モデルを実行して2グループを生成）。salva-appのplanに定義した契約 — 元音源と同SR・同長への揃え・マニフェスト形式・atomic publish — を維持。パッケージ版・checkpoint SHA256・推論設定もスクリプト側で固定する
- [ ] **最終構成全体で再測定**: 1曲あたりの実測時間（許容上限5分）・ピークメモリ・契約スモークを、単体候補の測定値の流用でなく**複合後のパイプラインとして取り直す**（複合構成は実行時間・メモリが合算になるため、枠別の勝者が個々に上限内でも全体で超え得る）
- [ ] **既存キャッシュの移行**: `manifestUsable()` はモデル名を判定に使わないため、スクリプト差し替えだけでは分離済み素材が旧demucsのまま使われ続ける。`StemCache.h` の `contractVersion` を bump して旧キャッシュを無効化する（manifestに `model` は既に書かれているが判定未使用。判定に足すよりversion bumpが単純）
  - **bumpは producer/consumer 同時に**: `separate.sh` は manifest へ `"contractVersion": 1` を直書きしているため、StemCache.h だけ上げると新しい分離まで `manifestUsable()` で失敗する。**StemCache.h と separate.sh の出力を同時に更新**し、両者の一致を固定するテストを **`salva_tests`（`mise run test:salva` で実行される別ターゲット。daw_testsではない — Salvaの境界維持のため分離済み）** に追加する（separate.sh を読んでリテラルを `StemCache::contractVersion` と照合する）
  - **旧キャッシュの掃除**: bumpは旧キャッシュを「使わなくする」だけで削除しない。startup sweepは同一identity内の未参照run削除のみのため、再分離しない素材の旧versionキャッシュが数GB級で不可視に残り続ける。sweepに削除処理を追加するが、**削除条件は「不一致」でなく `manifest.version < contractVersion` に限定**する（キャッシュルートはdev/release共有のため、「不一致削除」だと contract v1 の旧Releaseを起動した瞬間に v2 の新しいdevキャッシュが未来versionとして消される）。`salva_tests` で以下4ケースを固定:
    - 過去version・死んだlock → 削除
    - 過去version・生きたlock → 保持
    - 現行version → 保持
    - 未来version → 保持
