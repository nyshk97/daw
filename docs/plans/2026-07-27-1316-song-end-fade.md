# 曲末フェードアウト（マスターフェード）

## 概要・やりたいこと

曲の終わりで全体の音量を落としていく「フェードアウト」を、**プロジェクトに1本だけ**持てるようにする。

現状は各トラックのリージョンに個別フェードを引くしかなく、手数が曲末に残っているトラック数に比例する。他DAWの標準手段はマスターのボリュームオートメーションだが、LaLaはオートメーションを持たない方針。そこで**曲末フェード専用の1本**として、オートメーションの一般形を入れずに解決する。

判断の経緯と「なぜオートメーションの一般形を持ち込まないか」は `docs/design/region-settings.md` に書く（Phase 0）。planには残さない。

## 前提・わかっていること

### 確定した仕様（2026-07-27 の `/dig-lite`）

| 項目 | 決定 |
|---|---|
| カーブ | S字（raised cosine）`g(t) = 0.5 * (1 + cos(π t))`、t ∈ [0,1] |
| 作成 | **再生ヘッド位置**を開始点にしてショートカット。終端は最後のアイテムの終わりへ自動吸着 |
| 編集 | 両端をルーラー上でドラッグ（サイクル範囲と同じ ±4px 判定） |
| スナップ | **する**（1/16上限のグリッド。`xToCycleSixteenths` を流用） |
| 表示 | フェード区間はカーブに沿ったシェード。**終端以降はレーン全域を薄い「無音領域」で覆う** |
| 終端 | 置いた位置で固定（曲を伸ばしても追従しない） |
| 本数 | プロジェクトに1本のみ |
| 保存形式 | **v12**（現在 v11） |
| undo | 対象にする（`UndoStack::State` の拡張が必要。下記） |
| 位置の保持 | **1/16単位**でモデル・スナップショットの両方に持つ。サンプル換算はエンジンが毎ブロック行う（BPM/SR追従のため。下記） |

**カーブがS字な理由**: 出だしと着地が緩やかなので、フェードが始まったことに気づかれにくく、無音への着地も目立たない。リージョンフェードは「リニア固定」と決めているが、あちらは20〜50msで知覚差が出ない一方、曲末フェードは10〜30秒あり明確に差が出る（振幅リニアだと最後の1割で -20dB → 無音まで落ちて「最後にスッと消える」印象になる）。後から差し替えるのは実質1行なので、実機で聴いて決め直してよい。

**スナップする理由**: リージョンフェードは「フェードは平滑化であって音楽的位置ではない」からスナップしないと決めたが、曲末フェードは「最後の8小節から」のように音楽的な位置で決めるもので性質が逆。

**終端を固定する理由**: 追従にすると触っていないのに位置が動く。固定すると「終端より後ろが鳴らない」事故が起こりうるので、無音領域の表示で防ぐ。

### 決めた細目

**位置は1/16単位で持ち、サンプル換算はエンジンが行う**

`PlaybackSnapshot` にサンプル位置を入れてはいけない。`applyBpmText()`（`MainComponent.cpp:1567`）は `transport.bpm` / `project->bpm` / `timeline.refresh()` を更新するだけで**スナップショットを再pushしない**ため、サンプル単位で持つと「表示は新しい小節位置へ動くのに音は古い位置でフェードする」状態になる。デバイスSR変更時も同じ。

- スナップショットには**1/16位置のまま**入れ、`PlaybackEngine` / `BounceRenderer` が現在の bpm / sr で換算する
- これは MIDI ノート（ppq で持ってエンジンが換算）と同じ性質で、BPM追従すべきものの既存の扱いに揃う
- 換算は **`llround` の整数サンプル**に統一し、RT とオフラインで同じ規則で書く（GOTCHAS.md:135「片方だけ直すと再生とバウンスの出力一致が崩れる」）

**自動終端（`⌃F` 実行時）の算出規則**

- 対象は**アイテムの見た目上の終端**。オーディオは `Clip::totalLengthSamples()`（**ループ込み**）、MIDIは `MidiRegion::totalLengthPpq()`（同じくループ込み）
- **リージョンミュートは除外する**（「この部分は使わない」という恒久的な意思表示）
- **トラックミュート・ソロは考慮しない** — 一時的なモニター状態であって曲の長さではない。トラックをミュートして作業中に `⌃F` を押したら終端が変わる、という驚きの方が大きい。バウンス範囲の算出（`MainComponent.cpp:1670` の `audible` 判定）とは規則が違うので、共用せず別実装にする
- **One Shot のテールは含めない** — バウンス範囲がサンプル全長を含めるのは「鳴り切るまで書き出す」ためで、見た目上の終端とは目的が違う。テールがフェード終端をまたいで切れても、その時点でゲインは既に0なので実害がない
- **終端の1/16への変換は切り上げ**（`ceil`）。最近傍だと終端が手前へ吸着して最後の音を切る
- **開始点は「表示中の最小グリッドへ最近傍で丸める」**（`xToCycleSixteenths` と同じ規則。ズームが浅ければ小節単位に丸まるが、「最後の8小節から」という決め方と合うのでむしろ望ましい）。切り上げ/切り捨てにする必然性はない
- **判定は必ずスナップ後の値で行う**。生の再生ヘッドが終端の手前でも、丸めた結果が終端と一致することがある:
  1. 開始点をグリッドへ丸めて `snappedStart` を得る
  2. `snappedStart >= end` なら no-op
  3. それ以外で作成／更新する
- **no-op にする条件**（何もせず `Log::info` だけ残す）: アイテムが1つもない / `snappedStart >= 算出した終端` / 既存フェードがあり `snappedStart >= その終端`
- **開始点の取得元は経路で違う**: `⌃F` は再生ヘッド位置、ルーラー右クリックの「ここから曲末までフェードアウト」は**右クリックした x 座標**。どちらも上と同じ規則で丸める

**表示（レビュー指摘5を受けて変更）**

digでは「終端より後ろのアイテムを減光」と決めたが、**終端以降をレーン全域の「無音領域」として薄く覆う**方式に変える。終端をまたぐアイテムは後半だけが鳴らないので、アイテム単位の減光では見た目と出音が一致しない。領域で覆えばまたぐアイテムも正しく表現でき、既存の `dimmed` 経路に条件を足す必要もなくなって実装も減る。

**バウンスの終端（テール処理を含む）**

曲末フェードの終端は「曲そのものの終端」なので、出力終端を**フェード終端に厳密に固定する**。

- **サイクルOFF かつフェード設定中**: `request.endSample = fadeEndSample` **かつ `wantTail = false`**
  - `wantTail` を残すと固定終端にならない。`BounceRenderer.cpp:322` のテールループは `mixBusesAndMaster` → 書き込み → 無音判定の順なので、**判定前に必ず1ブロック（1024サンプル）書き込む**。フェード終端以降はゲイン0でも末尾に無音が1ブロック付く
  - テールを切って困らないのは、フェード終端でゲインが厳密に0だから（鳴り残ったノートの余韻も0が掛かる）
- **サイクルON**: 従来どおり。範囲はサイクルで上書きし、`wantTail` も従来の判断のまま。フェード係数自体は掛かるので、サイクル開始がフェード終端以後なら無音のWAVになるが、それは指定どおり
- この分岐により `startSample >= endSample` は発生しない

### 調査で分かった実装上の足場

- **`masterGain` の通常経路は `PlaybackEngine.cpp:453-459` の1箇所だけ**。`298/300/305/381/383/388/390` は `canProcess == false` のときの縮退フォールバック（巨大ブロック時の緊急経路）
- `processSegment` は既にサイクル分割でセグメント化されていて `segPos`（サンプル位置）を引数で受けている
- バウンス側は `BounceRenderer::mixBusesAndMaster` の `mix.applyGain(0, numSamples, request.masterGain)` の1箇所
- **クリック（メトロノーム）は post-master に加算されている**（`PlaybackEngine.cpp:464`）。したがってフェードの影響を受けない = モニター用なので意図どおり
- **保存形式は現在 v11**（`Project.h:254`）。曲末フェードは v12。互換確認は「v11以前は未設定として読む」
- **`UndoStack::State` は `tracks` と `markers` しか保持していない**（`UndoStack.h:85`）。Project直下に置く値は履歴に入らないので、**State にフェード両端を追加する必要がある**。`EditKind::clipValue` は「復元後にどう push するか」を選ぶ種別であって保存範囲を広げるものではない（両方必要）
- サイクル範囲が前例として使える: モデルは `Project::cycleStartSixteenths / cycleEndSixteenths`（1/16単位のint）、JSONは `cycle` オブジェクト（`Project.cpp:424-428, 718-726`）、ルーラーのドラッグは `TimelineView::hitTestCycleEdge`（端±4px）と `xToCycleSixteenths`（グリッド吸着）。ただし**サイクルは undo 対象外**（`onCycleChanged`）なので、undo まわりは前例にならない
- 自動テストは `Tests/TestsMain.cpp` にある

### `addFromWithRamp` の扱い（GOTCHAS.md:148）

- `endGain` は**区間の排他端で評価したエンベロープ値**を渡す（最終サンプルの値ではない）。クランプすると傾きが狂う
- **ブロックごとに絶対位置から `startGain` / `endGain` を評価し直す**設計にする。逐次加算だと誤差がランプ全長に積もるが、ブロック単位で評価し直せば誤差はブロック長で頭打ちになる
- ブロックサイズが変わると出力はビット一致しない。**再生とバウンスの一致テストは `1e-4` の許容誤差**で見る

### 再生ヘッドと再生開始位置の使い分け

`docs/design/transport-playhead.md` より、**作成の基準は再生ヘッド**（⌘T の分割・⌘V の貼り付けと同じ「編集の基準」）。再生開始位置ではない。

- 位置は `TransportState::uiPositionSample()` から取る（生の再生位置を読むとクリック直後の1バッファ分だけ旧位置になる）
- `uiPositionSample()` は0クランプしないので、編集側で `jmax` する

### ショートカット

- **`⌃F`** を新設する（Logicに対応するデフォルト割り当ては無い。曲末フェードはバウンスダイアログ内の機能なので独自になる）。`⌃M`（リージョンをミュート）と同じ ⌃ 系の並び
- `Source/ui/Shortcuts.h` のテーブルに1行足し、`MainComponent::keyPressed` では `Shortcuts::matches()` で判定する（KeyPress直書き禁止）
- ルーラー右クリックメニューの表記は `Shortcuts::keyText()` から生成する

### Phase 3: エンジン結線 [AI🤖]

- [x] `PlaybackSnapshot` にフェード区間を**1/16単位のまま**持たせ、`pushSnapshot` 系で埋める（無効は 0/0）。サンプル換算はエンジン側で毎ブロック行う — BPM変更（`applyBpmText`）もSR変更もスナップショットを再pushしないため、サンプルで持つと音だけ古い位置に取り残される
- [x] **フェード境界（開始・終端）でセグメントを分割する**。`PlaybackEngine.cpp:152-196` の既存ループ（「サイクル境界をまたぐブロックはセグメントに分割し、残サンプルが0になるまで繰り返す」）に境界を足す。**境界は「現在位置より厳密に後ろ」のときだけ採用する**:
      ```
      if (segPos < boundary && boundary < segPos + segLen)
          segLen = (int) (boundary - segPos);
      ```
      サイクルの `jmin` と同じ形にしてはいけない。サイクルは `segPos >= cycleEnd` で `segPos = cycleStart` へ**巻き戻す**から `segLen = 0` にならないが（`PlaybackEngine.cpp:195-199`）、フェードには巻き戻しがないので、無条件 `jmin` だと次ループで `segPos == fadeEnd` → `segLen = 0` → `done` が進まず**無限ループする**
      - **分割しないと境界を越えてランプが掛かる**。例えばブロックが `[end-256, end+256)` なら開始ゲイン > 0・排他端ゲイン 0 の直線が512サンプル全体に掛かり、**`end` 以後にも非ゼロが残る**（「終端以降は厳密に0」と矛盾する）。フェード開始側も同様に、開始前から僅かに減衰してしまう
      - 分割の結果、各セグメントは「フェード前」「フェード区間内」「フェード終端以後」のいずれかに**完全に収まる**
      - 外側で切るので、`canProcess == false` の縮退フォールバック（`298-390`）でも終端以後が確実に0になる。縮退側は各セグメントの代表値による定数ゲインでよい（階段は残るが境界越えの誤りは消える）
- [x] `PlaybackEngine::processSegment` の最終出力（`PlaybackEngine.cpp:441-457`）をセグメントの種別で分岐させる。演算順序が変わると出力が微小に変わるため、**フェード前のセグメントは現行のコードをそのまま通す**
      - **フェード前 / フェード未設定**: 現行どおり `buffer.addFrom (..., mixScratch, ..., masterGain)`。メーターも現行の `mixScratch.getMagnitude() * masterGain` のまま
      - **フェード区間内**: `mixScratch` に `masterGain × フェード` のランプを適用してから `buffer.addFrom (..., 1.0f)`。`addFromWithRamp` の `endGain` は**区間の排他端**で評価し、`startGain` / `endGain` は毎ブロック絶対位置から計算し直す。メーターはランプ適用後の `mixScratch` から測る（フェード前のピークに代表係数を掛ける方式は、ブロック内で音と係数の最大位置がずれるため不正確）
      - **フェード終端以後**: 出力への加算をスキップ（厳密に0）。メーターも0を記録する。クリックは post-master なので影響を受けず、現行どおり鳴る
- [x] `BounceRenderer::Request` にフェード区間（1/16単位）を追加する。**RTと同じ条件式でフェード境界でブロックを分割**し、`mixBusesAndMaster` をセグメント種別で分岐させる。フェード前は現行の `applyGain` のまま、区間内のみ `applyGainRamp`（排他端・絶対位置評価）、終端以後は0。テールにも掛ける場合は `rangeEnd + tailRendered` を絶対位置として評価する
- [x] **バウンス本編ループの `pos` の進め方を `pos += renderBlockSize` → `pos += n` に変える**（`BounceRenderer.cpp:241`）。現行は最終ブロックの端数でしか `n` が短くならないので固定幅で足りているが、境界で短縮すると**境界後のサンプルを飛ばす**。ループ本体は `scheduleBlockMidi (..., pos, n, tps)` / `renderSynthInto (..., n)` と既に `n` を使っているので、`pos` の進め方だけ直せば整合する
- [x] 短いブロック（`n < renderBlockSize`）がフェード境界ごとに発生する点に注意する。既存も最終ブロックで起きているので許容範囲だが、専用synthは `renderBlockSize` で `prepareToPlay` 済み（`BounceRenderer.h:30`）なので、可変長で問題が出ないことを確認する
- [x] **サイクルOFF かつフェード設定中**は `request.endSample = fadeEndSample` かつ **`wantTail = false`** にする。`wantTail` を残すとテールループが無音判定前に必ず1ブロック書くため、末尾に無音が付いて固定終端にならない（`BounceRenderer.cpp:322`）
- [x] サイクルONでは従来どおり（範囲はサイクル優先・`wantTail` も従来の判断のまま）
- [x] カウントイン中（`segPos` が負）はフェード前として係数1.0

## ログ

### 試したこと・わかったこと

- **回帰ハッシュが変更前後で完全一致**（`hash-engine: 59c79a3b0352743f` / `hash-bounce: 96f5e41dc31e0732`）。フェード未設定時の出力がビット一致で不変であることを実証できた。変更前の値は `git stash` で作業ツリーを退避して採取（手順は VERIFY.md に追記）
- **S字をブロック単位で線形近似する誤差は、直線ランプの誤差とは別物**。GOTCHAS.md の `1e-4`（同一傾斜内の分割による加算順序差）は当てはまらず、実測は RT(512) vs バウンス(1024) で **1.5e-3**、ブロック512 vs 500 で 3.5e-4。誤差は区間長の2乗に反比例するので、テストのフェードが短いほど大きく出る（当初 1800サンプル＝3.5ブロックで書いて中点の値が合わず、実使用に近い 0.3秒＝28ブロックに直した）。GOTCHAS.md に追記済み
- **`SongFade::sixteenthsToSamples` は bpm を `jlimit(20, 400)` でクランプする**（`TimelineView::barLengthSamples()` と規則を揃えるため意図的）。テストで 480BPM を使って位置が合わず気づいた
- **UI描画のピクセル検証は見送った**: `drawSongFadeShade` をテストするには `TimelineView.cpp` をテストターゲットに足す必要があり、UIの `.cpp` を含まない既存の構成（テストを軽く保つ設計）を壊すため。カーブの値自体は `gainAt` のテストで担保されているので、暗幕の見た目は人間の動作確認へ回した
