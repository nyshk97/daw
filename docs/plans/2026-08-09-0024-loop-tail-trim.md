# ループ素材のテール検知 — 余韻・パディング付き書き出しの小節推定とクリップ整形

## 概要・やりたいこと

「Cymatics - Eternity Piano Wet 6」型の素材への対処。ファイル尺はちょうど6.00小節だが音楽は4小節で、
残り2小節はリバーブの余韻（-36dB）と書き出しパディング（-91dB）。現状は index がファイル尺から
6小節と推定するため、①アンカーが6小節になり進行グリッドとチップ表示が間延びする
②採用で敷いたクリップの後半2小節が無音のままループし、ビートとして不自然（実使用で発覚）。

対処は2段:

1. **index の小節推定にテール検知を足す** — 末尾の静かな小節を音楽長から落とす（アンカー・
   進行検出・表示が正しくなる）
2. **採用時にクリップをループ長で刻む** — 音楽長ぶんだけをループ区間にし、余韻は切り落とす
   （次の周回の頭にマスクされる。境界のクリック防止に短いフェードを焼き込む）

"Wet"系（リバーブ込み書き出し）の素材には同類が多く、ライブラリが増えるほど踏む頻度が上がる。

**既存プロジェクト・既存アンカーの移行は考えない**（全部テスト段階の楽曲と本人明言。
2026-08-09 確定）。

## 前提・わかっていること

- 実測（Piano Wet 6・90bpm・16.00s = 6.00小節）: 小節別 RMS は
  1〜4小節 = -10〜-14dB / 5小節 = -36.2dB / 6小節 = -90.8dB（いずれもピーク比）。
  実音とテールの差が20dB以上あり、閾値設計に余裕がある
- **全小節に実音がある素材を誤爆しない**こと（合成テスト②と、推定が変わった素材の全件試聴で
  確認する）。~~例: Eternity Acoustic Guitar Loop Wet 4 は6小節目まで音がある~~
  → 2026-08-09 実測で**誤認と判明**: この素材の5〜6小節は RMS -52.8/-95.4dB・ピーク
  -31.3/-83.1dB の純然たるテールで、音楽長は4小節が正しい（「6小節」は旧・尺ベース推定を
  信じた前提だった。実装レビュー指摘で確定）
- `index.py` の `loop_bars_estimate` は現状ファイル尺ベース。size+mtime が同じエントリは
  再分析しないため、**ロジック変更を既存エントリに効かせるには版の繰り上げが必要**
- 採用時の `--bars` は index の推定値を優先し、無いときだけ wav 実尺の切り下げ
  （MainComponent::adoptLoopCandidate）。index が4を返せば looproots のグリッドも4小節になる
- クリップ配置は現状「バッファ全長を敷く」（`GachaSession::previewLoopCandidate`・
  `loopCount=1` で2周）。Clip には `lengthSamples` / フェード機構が既にある
- 判断ロジックは ui/ に置かない（CLAUDE.md）— バッファの刻み計算は shared/ のヘルパーに
  切り出して daw_tests で固定する
- 敷くだけ（BPM逆コピーなし）でも刻み長は**ループ自身のBPM**から計算するので、
  プロジェクトBPMに依存しない

## 実装計画

### Phase 1: index.py のテール検知 [AI🤖]

- [x] `loop_bars_estimate` にテール検知を追加: 小節を後ろから見て、**RMS と小節内ピークの
  両方**が閾値以下（RMS **-30dB** かつ ピーク **-12dB**、いずれもファイル全体ピーク比。
  当初案のピーク -20dB は実測で余韻小節の頭に負けた — ログ参照）の小節だけを落とす。残りが1小節未満になる場合は落とさない（全体が静かな素材を0小節にしない）。
  RMS 単独だと「最後に短い音が1つだけある疎な小節」（無音時間が平均を下げるが音楽的には必要）を
  テール扱いする — ピーク条件が「意図した音が1つでもあるか」を守る。**曖昧なら切らない**へ倒す
  （プランレビュー指摘）
- [x] 端数の扱い: テール落とし後の長さで丸め規則を通すが、**切り上げ方向（実尺が推定小節長より
  短い）は不足が絶対時間で 30ms 以内のときだけ許す**（±8%は比率条件として維持）。
  8%は絶対時間だと 90bpm・4小節で約0.85秒・40bpm なら約1.9秒になり、Phase 2 の無音埋めで
  毎周その長さの穴が開く（プランレビュー指摘）。**30ms を超える不足は
  `loop_bars_estimate` を「不明」にする** — floor に倒すと最大ほぼ1小節の実音を切ることになり
  「曖昧なら切らない」と矛盾する（プランレビュー指摘で floor 案を撤回）。整数化に使ってよい
  不足は「テール（余韻・無音）として説明できるもの」だけ。フェードアウトで終わる素材
  （最終小節が -20dB 前後まで減衰）は**落とさない**側に倒す — 閾値は「明らかな余韻・無音」
  だけを対象にする
- [x] **採用時の floor フォールバック（MainComponent 側）は削除する**: index が同じ 30ms
  規則で判定するようになるので、UI 側の再判定は二重実装（しかも「判断ロジックを UI に
  置かない」の自己違反 — プランレビュー指摘）。`candidate.loopBars == 0`（推定不明）は
  そのまま採用不可とし、UI は「ループ長を判定できないため採用できません」のアラートを
  出すだけにする（アンカー＝グリッドの土台なので、正しくない小節数で敷くほうが害が大きい）
- [x] index の版を繰り上げ、旧版エントリは size+mtime が同じでも再分析する配線
  （次回 `mise run lib:index` で全件更新・以後は差分のみ）
- [x] テスト（合成wav）: ①4小節音楽＋2小節無音 → 4 ②全小節に音がある6小節 → 6
  ③最終小節がフェードアウト（-20dB台）→ 落とさない ④全体が静かな素材 → 1小節未満に
  しない ⑤**最終小節が短い単発音1つ（高ピーク・低RMS）→ 落とさない**
  ⑥**30ms 境界: 29ms 不足 → 推定小節数を返す / 31ms 不足 → 不明**（Phase 2 のヘルパー
  テストだけでは上流の丸め規則の退行を検出できない — プランレビュー指摘）
  ⑦旧版エントリの再分析が走る

### Phase 2: 採用時のクリップ刻み [AI🤖]

- [x] shared/ にバッファ刻みヘルパーを追加（static・daw_tests 対象）:
  入力 = バッファ・レート・ループBPM・ループ小節数、出力 = **常に「loopBars × 小節サンプル数」
  ちょうどの長さ**のバッファ（長ければ切り詰め・短ければ末尾を無音で埋める）。
  短い側を「無傷」にすると反復間隔が実バッファ長になり、小節グリッドから周回ごとにヨレる
  （プランレビュー指摘）。**無音埋めの上限は 30ms** — Phase 1 の 30ms 条件（丸め規則）が
  上流でこれを保証する。**ヘルパーは失敗可能な戻り値にし、
  上限を超える不足は失敗を返す → `previewLoopCandidate` 自体を失敗させて採用を中止する**
  （ログだけ残して元バッファのまま成功させると、ヨレるクリップがそのまま採用され
  「常に目標長」の契約と矛盾する — プランレビュー指摘。上流の条件が正しければ到達しない
  防波堤で、到達したら推定バグの検出器になる）。
  **フェードは切り詰め・無音埋めが実際に起きたときだけ**掛ける: 目標長とサンプル単位で
  一致する入力は**完全に無変更**で返す（シームレスに作られた正常素材が大多数で、常時
  焼き込むと元々なかった継ぎ目＝毎周のアタック減衰と音量低下を作ってしまう —
  プランレビュー指摘）。掛ける場合、フェードアウトの終端は min(入力長, 目標長) に置いて
  その直前 15ms の**原音**に適用し、その後ろを無音で埋める（無音埋め後の出力末尾に掛けると
  フェード対象が既に無音で原音→パディング境界の不連続が残る）。フェードインは先頭 3ms
  （いずれも耳チェックで確定）。
  **刻みは `previewLoopCandidate` が状態を変更する前に実行する**: 失敗時は Project も
  GachaSession も完全に不変（baseline 未保存・トラック未作成・ベース仮配置も無傷）で
  false を返す — トラック作成後に失敗すると巻き戻し処理の数だけ漏れが生まれる
  末尾フェードだけだと境界が 0 → 非0 の不連続になりクリックが残る（`loopCount` は同一
  バッファの単純連結で、Clip のフェードは連なり全体の両端にしか掛からない — プランレビュー
  指摘）。クロスフェード方式は連結時の重ね合わせ機構が無く工事が大きいので、両端フェードで
  始め、耳チェックで不足なら再検討
- [x] 適用場所は **`GachaSession::previewLoopCandidate` の中**（`input.anchor` の
  loopBars/bpm と `input.audioSampleRate` から計算）。`placeLoopPreview` だけで刻むと、
  SR未確定プロジェクトでデバイスレートが変わったときの keep 直前再変換経路
  （ライブラリ原本を再読込して直接 previewLoopCandidate に渡す）でテールが復活する
  （プランレビュー指摘）。keep の実体化は刻み済みバッファを書くので `clip-NNN.wav` も
  音楽長になる — 追加工事なし
- [x] daw_tests: **出力長 = loopBars × 小節サンプル数と厳密一致**（長い素材の切り詰め・
  短い素材の無音埋めの両方。「反復間隔がグリッドと一致する」ことの固定）・
  **目標長と一致する入力はサンプル単位で無変更**（正常素材にフェードを焼き込まない）・
  フェードは刻みが起きたときだけ両端に効く・**末尾が非0の短い入力**で原音→パディング境界が
  連続（フェードで0に落ちてから無音になる）・**30ms超の不足はヘルパーが失敗し
  `previewLoopCandidate` が false を返して Project・GachaSession とも完全に不変**
  （baseline 未保存・トラック未作成・既存のベース仮配置も無傷）・
  **先頭サンプルが非0の合成音**で `loopCount` 展開の繋ぎ目に不連続が出ない・**異なる audioSampleRate のバッファで `previewLoopCandidate` を2回呼び、
  2回目（SR再変換の差し替え相当）も刻まれている**こと（keep 直前の再読込判断は
  MainComponent 側で daw_tests はUIをリンクしないため、テストは GachaSession の
  呼び出しで表現する — プランレビュー指摘）

## ログ

### 試したこと・わかったこと

- 2026-08-09 実装完了。全ライブラリ再インデックスの結果: **推定変更 38本 / 416本、うち None 化5本**
  （5本の内訳: 対照群2本＝採用対象外・実ループ3本＝実尺 4.31小節等の「音楽が整数小節に
  乗っていない」素材で規則どおりの判定）。Wet 系は全て音楽長に落ちた（Piano Wet 6: 6→4 等）
- **想定外1: リサンプルの丸めで「1サンプルだけの部分小節」ができ判定が壊れる**。実尺ちょうど
  4.0000小節のファイルが librosa の 22050Hz 変換で 4.0000076小節になり、1サンプルの小節5の
  RMS(-28.3) が閾値を割らず None 化（49本誤爆）。30ms 以内のはみ出しを端数に数えない処理を
  追加（切り上げ許容30msと対称）
- **想定外2: ピーク閾値 -20dB では余韻小節を落とせない**。余韻小節の頭は減衰の始まりで
  ピーク -15.3dB（実測）。-12dB に緩めた — 意図した音はほぼ確実にこれより大きい
- 2026-08-09 実装レビュー4件を反映: ①「Acoustic Guitar Wet 4 = 本物の6小節」は前提の誤認と
  確定（前提節を訂正） ②刻み失敗が cancelGachaPreview の後に起きると既存のドラム・ベース
  仮配置だけ失われる → placeLoopPreview で**プリフライト刻み**（撤去より前に検証。内部の
  再刻みは「一致→無変更」で素通り） ③looproots の --bars 省略経路が estimate_bars の
  シグネチャ変更で TypeError → 修正＋CLI テスト追加 ④applyGainRamp の endGain は排他端の値で
  1→0 指定だと最終サンプルに残差 → 排他端値の指定＋最終サンプルの明示ゼロ化、テストを
  フルスケール入力・厳密0判定に強化
