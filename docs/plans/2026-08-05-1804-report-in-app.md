# 分析レポートのアプリ内生成・閲覧

## 概要・やりたいこと

リファレンス分析レポート（`references/<名前>/report.md`）の**生成**（`report.sh` = Claude Code ヘッドレス実行）と**閲覧**を LaLa の中で完結させる。

- 背景: レポートを読むために Obsidian / ターミナルへ跨ぐのが実使用で認知的負荷になっている。`docs/design/reference-beat.md` に書いた「アプリ内描画は当面やらない」の判断変更条件（実際に読んだ上で切れ目と感じたら）が満たされた
- これは「アプリ内の分析表示UIは作らない」原則の**例外第1号**。ただし開いたときだけの別ウィンドウで、メイン画面に情報は常駐しない
- 将来の勝ち筋（今回はやらない）: レポート内 `listen/` の wav リンクをインターセプトしてアプリ内試聴 →「耳で検算」がその場で回る

## 前提・わかっていること

`/dig`（2026-08-05）での決定事項と調査結果。

### スコープ

- **生成＋閲覧の両方**。試聴連携は今回入れない（wav リンクは外部デフォルトアプリで開くだけ）
- 導線は**ガチャパネルの参照行**（リファレンス一覧 ComboBox が既にある場所）。リージョン右クリックには置かない（分析後のリージョン→references フォルダの紐付けは保存されないため）

### 閲覧の設計

- **`WebBrowserComponent`（WKWebView）一択**。JUCE 8.0.9 に Markdown レンダラは無く、`AttributedString` は表が組めない（`docs/design/reference-beat.md` で調査済み）
- `juce_gui_extra` の追加リンクが必要（現状は `juce_audio_utils` のみ）。WebKit.framework も
- **Markdown→HTML 変換は Python 側**: `tools/reference/render_report.py` を新設。pip `markdown` を requirements.txt に追加。CSS・`analysis/` の図を**インライン埋め込みした自己完結 `report.html`** を出す（WKWebView の file:// ローカルリソース制限を最初から回避）。配色は LaLa の Theme に合わせたダーク
- 変換は**開くときに mtime 比較でオンデマンド**・同期待ち（数百ms）。report.sh 側には足さない（二重管理を避ける）。HTML はただの派生キャッシュ（過去の3曲もそのまま読める）
- ウィンドウは **MixerWindow 同型の1枚使い回し**（DocumentWindow・閉じる＝非表示・位置サイズはセッション内維持）。別リファレンスを開くと内容が入れ替わる
- **読み物専用と割り切る**: LaLa ショートカット（Space 再生等）の転送はしない。テキスト選択・⌘C・スクロールは WKWebView 標準で効く（⌘F 検索は素の WKWebView に UI が無い可能性が高く、Phase 1 で実測して決定）
- Hardened Runtime: WKWebView の JS は Apple 署名済みの別プロセス（WebContent）で走るため、アプリ本体に JIT 系 entitlement は通常不要の見込み。ただし `scripts/build.sh`（Sparkle XPC の inside-out 署名と共存）での実地検証をスパイクで先にやる

### 生成の設計

- **手動トリガー**（分析との自動連鎖はしない。ガチャ用にカードだけ欲しい分析ではトークンを使わずに済む）
- 参照行の下に**状態遷移するボタン1個**: report.md 無し→「レポートを書く（10〜15分・AI）」／有り→「レポートを開く」。**書き直しはボタン右クリック**メニュー＋上書き確認
- **多重起動不可**（生成走行中は他リファレンスの生成も無効）。ガチャの振り直しは別プロセスなので並行可のまま
- 生成中はボタンの代わりに**経過行**（stream_progress の出力＋経過時間）＋キャンセル。**モーダルにしない**（15分をオーバーレイで待たせない。分析4分とはここが違う）
- 完了/失敗は**画面端トースト**（クリックでレポートを開く）。レポートウィンドウが**同じフォルダを表示中なら**自動再読込（別フォルダ表示中は切り替えない）
- **生成対象は card.json があるフォルダのみ**（ガチャパネルの既存列挙と同じ。card 生成は BPM ゲート通過が前提なので、「BPM が測れずレポートを書けない」ケースは UI 上選択できず、専用の文言も不要）
- **生成はトランザクション化**: 出力を `report.md.next` に書かせ、exit 0＋妥当性検査を通過したときだけ `report.md` へ atomic rename。成否判定は report.md の存在ではなくこのトランザクションの完了（書き直し時に古い report.md が残っていても誤って成功扱いにならない・失敗やキャンセルで正常な旧レポートを失わない）
- 生成中のアプリ終了・プロジェクト切り替えは**確認ダイアログ**（分析の黙ってキャンセルより慎重側。15分とトークンが飛ぶため）
- `claude` のパス解決: `report.sh` に「PATH に無ければ `~/.local/share/mise/shims/claude`」フォールバックを追加（shims は node バージョン非依存で安定。ターミナル実行と両立）

### コードベースの現状（調査済み）

- 分析の配管が流用できる: `SpawnedProcess` ＋ `MainComponent::pollReferenceAnalysis()` のポーリング方式・キャンセル・行ストリーム表示
- ガチャパネルの参照列挙は `GachaPanelView::refreshCards()`（`references/*/card.json` があるフォルダのみ）
- `ReferenceTools`（`Source/shared/ReferenceTools.h`）にスクリプトパス解決と available 判定の置き場がある
- `report.sh` は `claude -p` を stream-json で流し `stream_progress.py` で人間可読行にして stdout に出す（3曲ヘッドレス完走済み）
- 判断ロジックは shared/ へ（`daw_tests` は UI の .cpp を含まないため）: report 状態判定（無し/生成中/あり）・変換要否（mtime 比較）をテスト可能な形に切り出す

### Phase 4: レポート生成（report.sh の起動） [AI🤖]

- [x] `report.sh` の改修（ターミナルからの手実行が壊れないことも確認）:
  - claude パスのフォールバック（PATH に無ければ `~/.local/share/mise/shims/claude`）
  - **トランザクション化**: プロンプトの出力先を `report.md.next` に差し替え（`TOOLS/` と同じ sed 置換方式）→ exit 0 かつ妥当性検査（ファイルが存在し、見出しを含む非自明なサイズ）を通過したときだけ `report.md` へ atomic rename ＋ **report.html を削除**（キャッシュ無効化）。失敗・中断時は `.next` を削除して旧 report.md / report.html を維持
  - **フォルダ単位のロックで排他**（「多重起動不可」はアプリ内フラグだけでは足りない — アプリ生成中にターミナルから report.sh を手実行するケースがある）: **`/usr/bin/lockf` の fd 形式**（macOS 標準搭載。`flock` CLI は macOS に無い）で、リファレンスフォルダ内のロックファイルを report.sh 自身が保持する:
    ```sh
    exec 9>"$LOCK_FILE"
    /usr/bin/lockf -s -t 0 9 || { echo "別のレポート生成が走行中です" >&2; exit 75; }
    ```
    **command 形式（`lockf ... <lockfile> <command>`）は使わない** — ロック所有者が外側の lockf プロセスになり、killpg の SIGTERM で lockf が先に死ぬと内側の EXIT cleanup 完了前にロックが解放され、後発の新しい `.next` を旧プロセスの cleanup が消すレースがある。fd 形式ならシェル自身が fd 9 を保持し、cleanup 中もロック維持・シェル終了で自動解放・SIGKILL でも即解放（実測済み: 保持中の2本目= exit 75・解放後= exit 0）。flock(2) ベースなので**アプリ側は同じファイルへ C++ の `::flock (fd, LOCK_EX | LOCK_NB)` で相互運用できる**
  - **クリーンアップはシグナル任せにしない**（アプリのキャンセルは killpg SIGTERM →1秒→ SIGKILL。SIGKILL では trap も走らない）:
    - **ロック取得後に**前回クラッシュ由来の古い `.next` を削除（ロック下なので、生きている実行の出力を消す競合は起きない）
    - `EXIT` trap は「存在すれば `.next` を削除」。`HUP/INT/TERM` のハンドラは cleanup 後に対応する非0コードで exit する（return しない）
    - 順序: 妥当性検査 → **trap を有効にしたまま** atomic rename → 成功後も EXIT cleanup はそのまま走らせて無害（`.next` はもう無い）→ ロック解放。mv 失敗時も trap が `.next` を回収する
    - アプリ側の join 後掃除（SIGKILL の取りこぼし対策）は **`::flock (LOCK_EX | LOCK_NB)` でロックを取れたときだけ** `.next` を削除する（手動実行が走行中ならロックが取れず、触らない）
  - シェル側テスト（`tools/reference/tests/`・**fake claude** を差し込んで実行）: 成功時だけ旧 report.md を置換し html を削除する／exit 非0・妥当性検査失敗・SIGTERM では旧 md/html を維持し `.next` を残さない／起動時に古い `.next` があっても影響しない／**2本目の同時起動は拒否され、1本目の一時出力に触れない**（実際の `/usr/bin/lockf` を通して検証する）
- [x] `ReferenceReportGenerator`（新設・`ReferenceAnalyzer` と同型: `juce::Thread` ＋ atomic 状態 ＋ pull 型完了通知）: 内部で `SpawnedProcess::readUntilFinished()` を回し、`status() / currentLine() / cancel() / cancelAndWait() / takeResult()` を公開。**MainComponent の timer は generator の atomic 状態だけをポーリングする**（`readUntilFinished()` はブロッキング API なので UI スレッドから直接呼ばない）。fake script で成功・失敗・キャンセル・プロセスグループ終了を `daw_tests` で確認
- [x] ガチャパネルのボタン状態遷移: 無し→「レポートを書く（10〜15分・AI）」／生成中→経過行（stream_progress の最新行＋経過時間）＋キャンセル／有り→「レポートを開く」。生成中は他リファレンスの生成も無効
- [x] ボタン右クリックに「レポートを書き直す」（上書き確認ダイアログ→生成開始）
- [x] 完了/失敗トースト（画面端・数秒・クリックでレポートを開く。失敗時は要因の1行）。ウィンドウが**同じフォルダを表示中なら**自動再読込
- [x] アプリ終了・プロジェクト切り替え時の順序（**現状の `confirmCloseProject` は未保存確認より前に全ワーカーを同期キャンセルするので、単に並べて足さない**）:
  1. 生成走行中なら先に非同期で「レポート生成中です。中断して閉じますか?」を確認
  2. キャンセルされたら何もしない（**生成は継続する** — これを動作確認項目に含める）

  4. その後、既存のワーカーキャンセル→未保存確認フローへ進む
